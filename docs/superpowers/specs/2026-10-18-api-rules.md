# API rules for shadcn-egui components (draft)

Stage 2 draft of the plan `docs/superpowers/plans/2026-10-18-port-all-components.md`;
it moves into `plugin/skills/port-component/references/` with the stage 3
cleanup. Every component, the 14 existing ones included, follows these
rules. Examples sketch the target API, not today's code. Idiom references
name sections of the egui 0.34.3 idiom catalogue (§Widget builders, …).

## How to read these rules

- A rule states required behaviour and API shape. Where a rule names an
  egui mechanism, it does so in an *Implementation note*: the note is one
  way to build the behaviour, the behaviour is the requirement, and it
  holds in every way an app drives egui.
- A rule answers its question for every component. Before a component
  gets its own answer, the general rule is applied to it; where that gives
  an answer, the answer stands, and the D- entry records it as a
  consequence. A component never becomes a special case of a rule.
- Lists and named components in a rule are examples of its clause, never
  its definition. A component the rule does not name is decided by the
  clause.
- A port reads these rules, then, in
  `docs/superpowers/specs/2026-10-18-api-decisions.md`, its family bundle
  (D-109 to D-126; the title names the components) and its verdict entry
  if it has one (D-103 to D-108): their default proposals apply until the
  family PR decides. Other D- entries ("Depends on D-n") it opens only for
  options and reasons. A rule states the maintainer's decision, also where
  it differs from the entry's recommendation; where an entry's text and a
  rule differ, the rule wins, and the entry's **Consequence** says what
  changed. A rule that rests on a deferred bundle line stays a draft
  until the family PR decides.
- The porting standard (`plugin/skills/port-component/SKILL.md`) is the
  second read. Where it and these rules differ, these rules win; the
  cleanup brings the standard in line (design, Stage 3).
- **Open (M-n)** marks a choice the principles do not settle. It lists
  the options and a recommendation; the recommendation applies until the
  maintainer decides.

## Guiding principles

The maintainer accepted these principles on 2026-10-19 (exact wording);
the decisions apply them, and a later port weighs an open question
against them.

- **P1** One consistent API across all components beats completeness:
  when two answers both work, pick the one every component can follow.
- **P2** Use egui's own idiom for the API shape where egui has one
  (builder with `#[inline]` setters, `impl Widget` for leaves,
  `show(ui, closure) -> InnerResponse<R>` for containers, `ui.add_enabled`
  for disabled state, a required binding in the constructor and an
  optional one as a setter), so an egui user can guess the API.
- **P3** Where egui is itself inconsistent, pick one predictable rule.
- **P4** Behaviour and looks follow shadcn upstream at the pins; egui
  decides only the API shape. ("We should not copy egui behavior ... we
  copy shadcn behavior!") The theme may change the look of plain egui
  widgets, not their behaviour.
- **P5** The Rust compiler catches misuse: no stored closures that borrow
  the body's state, no orphan-rule tricks, distinct types where meanings
  differ, so a mix-up does not compile.
- **P6** Before 1.0, correctness beats small breakage. Renames are fine —
  there is no installed base yet. Every break gets a CHANGES.md entry
  that tells users how to upgrade.
- **P7** Minimal dependencies: each new crate is an optional feature and
  needs the maintainer's consent.
- **P8** Decide only what is needed now: crate-wide choices now (the 0.7.0
  cleanup needs them); family-specific choices may wait for the family's
  PR.
- **P9** Colours match upstream exactly; a look that cannot reach the
  exact colour is not acceptable.

## Builder shape

- A component is a short-lived builder: `new(..)` takes the required data,
  chained `#[inline]` setters `fn x(mut self, ..) -> Self` set options,
  and it is consumed by `impl Widget` (leaf) or `show(..)` (container).
  `new` is `#[inline]` too, and a `new()` without arguments comes with a
  `Default` impl. Every builder carries `#[must_use]` with egui's message.
  Every variant and size enum of one component derives `Clone, Copy,
  Debug, Default, PartialEq, Eq` with upstream's default as `#[default]`;
  data-carrying enums derive what their fields allow; shared enums
  (`Orientation`, `Side`) have no `Default`, their default is per
  component. Variant and size enums are `#[non_exhaustive]`, closed sets
  are not. Depends on D-14, D-131.
- A flag setter takes a `bool`: `.invalid(bool)`, `.expanded(bool)`. A
  setter without an argument exists only as a shortcut for one value of
  an enum setter: `.vertical()` is `.orientation(Orientation::Vertical)`.
  A flag that defaults to `true` keeps its positive name and is called
  with `false`. No positional `bool` parameters. Depends on D-3, D-16,
  D-17.
- Mode constructors: `new` for the common mode, a named constructor per
  other mode or alternative content (`Accordion::multiple`,
  `Kbd::icon_only`); `from_*` names an alternative input form
  (`Progress::from_value`, `Pagination::from_count`), as egui's
  `ComboBox::from_label`. Icon-only content is such a mode, never a flag:
  `X::icon_only(.., icon, name)` with `name` as the accessible name, on
  every component (P1). Where upstream spells it as size variants (button
  `icon`, `icon-sm`), the mode picks the icon variant of the chosen size,
  and the size enum keeps the text sizes only: `ButtonSize` loses `Icon`,
  `IconXs`, `IconSm` and `IconLg` (maintainer, 2026-10-20). Modes that
  take different setters are separate types, so a setter that only one
  mode understands does not compile on the other (P5): `Calendar` and
  `RangeCalendar`, as upstream ships them. Depends on D-25.
- Text parameters take the type that fits what the component does with
  the text, whether a builder or a data item takes it: `impl Into<String>`
  when the component also reads it as data (filter, typeahead,
  comparison); `impl IntoAtoms` when the recipe lays the text out in one
  row that does not wrap, with icon slots (button, badge, kbd, toggle,
  toggle-group item, tab trigger), clickable or not; `impl
  Into<WidgetText>` for text that wraps (titles, labels, descriptions, an
  accordion trigger). *Implementation note:* a data item stores
  `Atoms<'a>` from `into_atoms()`; `&str` has no `Into<Atoms>`. A
  parameter that mirrors an egui parameter takes egui's type (`hint_text` as
  `TextEdit::hint_text`); a pick list's empty text is
  `placeholder(impl Into<WidgetText>)`. Icons by value (`Icon` is
  `Copy`), colours as `impl Into<Color32>`. Depends on D-15, D-2, D-19.
- A parameter of an egui type honours everything a value of that type can
  carry, as the egui widget that takes it does (image and text atoms,
  `atom_grow`, `RichText` attributes). What the crate cannot honour fails
  a `debug_assert!` that names it (`Atom::custom`), never silently (P5).
  Likewise a setter that compiles has its effect: a shared type (the
  generic data item) serves only where all its setters work, else the
  component has its own type; a setter that depends on another (a width
  on an icon-only button) is honoured or fails a `debug_assert!`. Depends
  on D-15.
- Disabled state comes from the `Ui` (`ui.add_enabled`, `add_enabled_ui`),
  as in egui (P2); a widget reads it from its `Response` in one place. A
  component also takes `.enabled(bool)` exactly when upstream gives it a
  `disabled` prop whose effect a disabled `Ui` does not reproduce (P4):
  the prop leaves part of what the component holds interactive (an
  accordion item's trigger is disabled, the caller's panel content is
  not), or the component has no `Ui` of its own that a caller could
  disable (a data item, an overlay on a caller's trigger). A disabled
  `Ui` does reproduce a prop that disables every interactive part a
  widget draws, as opacity comes from the style (Looks): tabs need no
  `.enabled`. `.enabled(false)` does what the prop does, no more; closure
  items take `add_enabled_ui`. Depends on D-1, D-79, D-80.
- An option setter for upstream behaviour or look exists exactly where
  upstream has the prop (dismissal, deselect) or a shipped demo changes
  the recipe value (a dimension), with upstream's default; where upstream
  has neither, there is no setter (toggle-group always clears). Setters
  the rules add for egui's sake (`id_salt`, `wrap_mode`, an own label)
  are named in their rule. Depends on D-23, D-41, D-78.
- Names: part functions and part types carry the component prefix plus
  upstream's part name (`card_title`, `menu_separator`, `TabsTrigger`,
  `SelectItem`); a crate type may share an egui type's name, a helper
  type with another meaning may not; shortcuts take content only, never a
  variant. Depends on D-20, D-18.
- No `#[deprecated]` aliases or forwards before 1.0: a rename or removal
  breaks at once, CHANGES.md gives the upgrade step (maintainer,
  2026-10-19; P6), and the 0.7.0 cleanup removes existing ones
  (`Input::id_source`, CP-06-8).

egui idiom: §Widget builders (builder struct + `impl Widget`, `#[inline]`
setters, `#[must_use]`), §Text, §Enabled state.

```rust

ui.add(Separator::new().vertical());
ui.add(Input::new(&mut email).hint_text("Email").invalid(email_bad));
```

## Looks

- The style is the single source of every visual value a crate widget
  paints: colour, opacity, size, spacing, line height, font. Values come
  from the active style's recipes, or from `Metrics` where upstream sets
  none (porting standard rule 5), and they hold for every style, a
  restyled one included, not only the shipped ones (P9). egui state
  (enabled, hover, focus, the `Ui`'s text colour) selects which recipe
  rule applies; an egui setting (`disabled_alpha`, `override_text_color`,
  `strong_text_color`, `weak_text_color`, `interact_size`) never decides a
  crate widget's or a crate layout helper's look (a crate row is as tall
  as its tallest item, as a flex row), and a crate container changes no
  egui setting for caller content that upstream does not set.
- A disabled part paints at the opacity its style's `disabled:` rules
  give, multiplied along upstream's part tree as CSS multiplies it, not
  along egui's `Ui` nesting: a part fn inside a container's content
  closure paints at container × part. A style that sets
  `disabled:opacity-25` shows 25 %, and a part with no `disabled:` rule
  stays opaque in a disabled `Ui`, as in a disabled `<fieldset>`.
  *Implementation note:* `Ui::disable` multiplies the painter's opacity by
  `visuals.disabled_alpha`, and `multiply_opacity` cannot raise it again,
  so a crate part sets its painter's opacity (`Painter::set_opacity`) to
  the `Ui`'s opacity with one egui disabled fade taken out, times its own
  value; one helper does this for every part. egui fades again on every
  nested disable (`add_enabled_ui(false)` inside a disabled `Ui` gives
  `disabled_alpha` squared), which the `Ui` does not report, so the helper
  removes one fade and the docs name the nested case. The theme sets
  `disabled_alpha` to its style's control opacity (`disabled:opacity-50`),
  which plain egui widgets show. Depends on D-1.
- Every piece of crate-drawn text and every crate icon resolves each of
  its attributes in one order: what the caller set on it explicitly (a
  `RichText` attribute, an icon's caller colour); else the recipe's
  value; else, for colour, the enclosing `Ui`'s text colour, which plays
  CSS's `currentColor`. egui's `strong` and `weak` are no explicit
  colours: on a crate widget such text takes the recipe colour. A crate
  container whose upstream sets a text colour or size for its content
  sets it on its content `Ui`, so crate text and plain egui widgets
  inside take it; what egui widgets cannot take (`leading-*`) reaches
  crate text only (D-100). The theme's global text colour for plain egui
  widgets never overrides a recipe colour. Depends on D-15, D-19, D-47.
- Crate text sits in its line box as Blink places it: baseline = line
  top + floor((line height − (A + D)) / 2) + A, with the font's ascent A
  and descent D each rounded to whole device pixels and the font's line
  gap unused when a line height is set; a text-entry field (`<input>`)
  rounds that half up instead. A and D come from the font's own tables
  (typo metrics where the font sets `USE_TYPO_METRICS`, else `hhea`), by
  one generic path with no per-font table; a caller's text without a
  line height takes the recipe's. An underline takes the colour of its
  own text run; images in content fade with their part. One text path
  does this for every component (Code and shared infrastructure).
- A font may carry a y correction (a `FontFiles` field, from
  `FONTS.tsv`), 0 by default; only a font whose capitals still differ
  visibly from Chrome's render on the path above gets a value. The test that measures text placement compares against a Chrome
  reference render (maintainer, 2026-10-20; this settles M-2).
- Boxes paint as CSS paints them. A fixed `h-*` or `w-*` is the border
  box (`box-sizing: border-box`): content larger than it overflows
  evenly, and the box does not grow. An outer `box-shadow` paints only
  outside the border box, so a transparent or translucent fill shows
  what lies under the box, never the shadow. *Implementation note:*
  egui's `Shadow` is a filled blurred rect; the recipe box clips it to
  the outside of the border box.
- Where egui has no primitive for a CSS look, the crate builds it from
  egui shapes to the browser's pixels. Where that is not possible, the
  port stops and states the case with its options to the maintainer; it
  never drops the look or ships an approximation silently (P9).
- A focus ring (`FOCUS_VISIBLE`) shows exactly when the browser's
  `:focus-visible` would: after focus moved by keyboard, not after a
  pointer press, nor after a focus move the crate makes in response to
  one (an overlay opened by click). The crate tracks the modality of the
  last focus change crate-wide (P4, P9). Depends on D-39.
- The theme may change the look of plain egui widgets (colours,
  spacing) only where it reaches upstream's exact colour, and never their
  behaviour (timing, focus, keys). It leaves plain `egui::ScrollArea` bars
  as egui draws them: a `ScrollStyle` thumb reaches only the nearest shared
  colour. Depends on D-135.

## Behaviour

- Defaults are upstream's (P4), also where egui's counterpart has another
  one: a separator is horizontal, a slider steps by 1 (`.step(0.0)`, egui's
  `step_by(0.0)` spelling, opts into a continuous slider), a menu trigger
  fires on pointer down. egui decides no default and no behaviour, and an
  egui layout never decides a component's default (a separator in a
  horizontal row is still horizontal unless the caller says
  `.vertical()`). A type's docs name each difference an egui user would
  not expect, and a `debug_assert!` catches the case that makes a widget
  silently useless (a slider step larger than its range, which leaves one
  position). Depends on D-112, D-116.
- Every per-pass mechanism (the overlay stack, Escape, focus return,
  hover timers, the heading font) behaves the same whether the app runs
  egui through `Context::run_ui` or through its own
  `begin_pass`/`end_pass` loop, and whether or not it called
  `Theme::apply`. A pass-start hook may give a mechanism its place in the
  pass, never its correctness: where no hook runs, the first crate call
  of the pass does the work. Tests drive both loops. The one allowed
  difference: previous-pass knowledge (Compound 6) relies on
  `request_discard`, so a loop without the discarded pass shows one stale
  first frame, which the docs say.
  *Implementation note:* egui runs `on_begin_pass` hooks and plugins only
  from `run_ui`. Depends on D-128.
- Pointer and keys act as on upstream's element in the browser. A press
  focuses, without a ring (Looks), what the browser focuses on press (a
  button, a tab trigger, a checkbox, bits' slider thumb), so keys work
  after a mouse press, an overlay returns focus to its trigger, and
  focus-bound behaviour follows (automatic tab activation selects on
  press). Activation keys are the element's: `<button>` Enter and Space,
  `<a>` (a link look) Enter only, bits checkbox Space only, switch both.
  No key upstream lacks; a key egui does not report on a platform (Meta
  outside macOS) is left out there, as the docs say. *Implementation
  note:* egui focuses no clicked widget and fakes a click for Space and
  Enter on any focused clickable widget.
- Units are egui's: durations are `f32` seconds (`.open_delay(0.7)`),
  lengths `f32` points (logical pixels), so a demo's Tailwind step becomes
  4 points per step (`spacing={1}` is `.spacing(4.0)`, `max-w-sm` is
  `.max_width(384.0)`).

## Compound components

How a Svelte compound component (`<Card.Root><Card.Header>…`) maps to
egui:

1. **Parts that only render data become builder setters** on the root:
   title, description, media (`Card::new().title(..)
   .description(..)`). Prefixed free part functions (`card_title(ui, ..)`)
   stay for custom layouts. A header action is a part fn inside the
   `show` closure (`card_action(ui, ..)`, D-48 (a')). Depends on D-46,
   D-48.
2. **The `show` closure holds the main content.** A secondary slot below
   it (footer) is a prefixed part fn inside the same closure
   (`card_footer(ui, ..)`, `dialog_footer(ui, ..)`), as upstream nests
   `Card.Footer` in `Card.Root`. Side slots (item and attachment actions) are the closure
   itself, because the main content there is setter data; bubble
   reactions are setter data. Footers keep upstream's direction and
   source order, and the caller nests a layout inside. Depends on D-47,
   D-48.
3. **Bound state and caller content.** The caller owns bound state; a
   component holds the `&mut` for its call, so a content closure that
   reaches the same owner (`self.method()`, the bound field) does not
   compile while the component holds it. A component whose upstream
   content is not inside a surface the component owns (tab panels beside
   the tab list, which only show the bound value) is a widget for what it
   draws plus a content part fn the caller calls after it, so the borrow
   ends before the content runs: `ui.add(Tabs::new(&mut self.tab, TABS));
   tabs_content(ui, |ui| match self.tab { .. });`. A component whose
   surface encloses the caller's content (modal, sheet, popover with a
   binding, accordion item, collapsible) keeps the binding for its call,
   as egui's `Window::open` does, and its docs show egui's local-copy
   idiom (`let mut open = self.open; …; self.open = open;`) (maintainer,
   2026-10-20, M-1 (a); P2). Depends on D-31, D-47.
4. **Items are data** when the widget needs them while it is closed or
   before it paints them (select and native-select: trigger text and
   typeahead; toggle-group; tabs list). A data item is an item type
   `XItem::new(value, content)` with setters (`.enabled`, `.icon`),
   named by the naming rule. Every item list takes `impl IntoIterator`
   of anything that converts into the item type: item values, `(value,
   text)` tuples, by value or by reference, so arrays, slices and
   iterators all serve the builder and the shortcut alike. Items carry
   plain values, also when the binding can be empty (T1). **Items are
   immediate-mode calls in the closure** when they can have arbitrary
   neighbours and carry the binding themselves (`radio_value`, menu
   items). A **handle** is passed to the closure when the parent holds the
   binding or places and separates items (accordion, breadcrumb,
   navigation-menu, message-scroller); its item method takes a value of
   the component's own item type, or a tuple that converts into it
   (`acc.item((1, "Shipping?"), |ui| ..)`). Repeated uniform children come as a
   count plus an index closure (carousel slides, resizable panes); small
   fixed sets are data lists (avatar group, input-otp `.groups`). Table
   rows come from a handle method that returns a row builder with flag
   setters (`.selected(bool)`), over columns declared up front. Depends
   on D-26, D-55, D-17, D-122, D-27.
5. **A crate widget inside a crate parent takes the parent's context by
   itself** (recipe, size, orientation, `invalid`, position in a group):
   a button in a button-group, kbd in a tooltip, an item in a menu,
   bubble alignment from message. No per-parent widget type and no extra
   argument; an explicit setter on the child overrides where a caller may
   disagree (calendar `.background(bool)`). *Implementation note:* the
   parent pushes a `UiStackInfo` tag, the child reads `ui.stack()`.
   Depends on D-57, D-56.
6. **Part functions follow one contract.** A container part fn
   (`card_footer`, `dialog_footer`, `card_action`) returns
   `InnerResponse<R>`, a passive part `Response` (T4). Parts are called
   in upstream's source order, which is also Tab and reading order: a
   part upstream places before the content (a header action) is called
   first, a footer last; a part out of that order is a `debug_assert!`.
   Whatever a container must know about a part or a child before it is
   drawn (an action's size, a child count, a position) comes from the
   item registry (T8); what it learns only after the closure (a footer
   was drawn) it uses after the closure only, without the registry and
   without a discard. A part tells its container that it exists only
   where a recipe styles that fact (T9).
   Depends on D-47, D-48, D-134.
7. **Root plus part types collapse into one widget** when the parts have
   no independent use (checkbox indicator, slider track and thumb, calendar
   grid). Depends on D-112.
8. **Upstream `Close` parts become `ui.close()`** (D-115, D-117).
   A `Provider` part's settings become the defaults or the root state of
   what it configures: the tooltip provider's delay becomes the crate
   tooltip's own default, upstream's 0 (D-40, D-130); the sidebar provider
   becomes the `Sidebar` root with state in memory (D-107).
9. **Groups without options are free functions** (`kbd_group`,
   `message_group`); groups with options are builders (`ItemGroup`).
   Depends on D-50.

egui idiom: §Containers (`show`, `InnerResponse`, `UiBuilder` stack info),
§Selection (`radio_value` runs), §Popups (`menu_button` items).

```rust
Card::new()
    .title("Create project")
    .description("Deploy your new project in one click.")
    .show(ui, |ui| {
        ui.add(Input::new(&mut name));
        card_footer(ui, |ui| { if ui.add(Button::new("Deploy")).clicked() { deploy(&name); } });
    });

    radio_value(ui, &mut plan, Plan::Free, "Free");
    radio_value(ui, &mut plan, Plan::Pro, "Pro");

    Tab::Account => self.account_ui(ui),
    Tab::Password => self.password_ui(ui),
});
```

## T1 · Selection

- A choice binds the caller's value: `&mut T` with `T: PartialEq`
  (+ `Clone` where the widget holds a list); multiple selection binds
  `&mut Vec<T>`. Domain values stay domain types (`f32`, `Date`, a
  1-based page). A component that owns and validates the answers itself
  keeps them in its own state type (questionnaire: indices in
  `&mut QuestionnaireState`). Depends on D-21, D-24, D-29, D-125.
- A choice that can be empty binds `&mut Option<T>` over data items of
  plain `T`; no data item is written `Some(..)`. Where the same widget also binds
  `&mut T`, the empty mode is a mode constructor
  (`Select::optional(id, &mut Option<T>, items)`); a widget that can
  clear its value by itself is empty-capable only (toggle-group single,
  accordion single, calendar single `&mut Option<Date>`). Depends on
  D-22, D-25.

  Immediate items of an empty-capable binding (`radio_value`, a menu
  radio item) carry the binding itself and keep their egui counterpart's
  parameters (T1 shortcuts, P2): over `&mut Option<Plan>` the item value
  is the binding's type, `radio_value(ui, &mut plan, Some(Plan::Free),
  ..)`. The plain-`T` rule serves data items, which the crate stores
  (maintainer, 2026-10-20).
- A value that matches no item marks nothing and shows the placeholder.
  Depends on D-22.
- Deselect by a second click behaves as upstream. Its setter (Builder
  shape) is `.allow_deselect(bool)` (select `allowDeselect`, calendar
  `preventDeselect` inverted), offered only where the binding can be
  empty. Depends on D-23.
- Value-editing widgets write the binding only in response to user input,
  then call `mark_changed()`; the caller reads `changed()`. A bound value
  off the step grid or outside the range shows at its nearest position
  and stays as it is until the user changes it (bits).
- Choice controls (checkbox, switch, radio item) take an optional own
  label, `.label(impl Into<WidgetText>)`, drawn through the Label text
  path (`RichText` attributes kept) and composed with the control as that
  control's upstream demo composes the two, with that demo's gap per
  control from `Metrics`; it wraps as Label does, in the width beside the
  control, and a press on it acts on the control (`<label for>`). A
  shortcut with an egui counterpart takes that counterpart's name and
  parameters in its order (P2: `checkbox`, `radio_value`, `toggle_value`),
  the others take the component's name and follow the same order (P1):
  `checkbox(ui, &mut b, text)`, `switch(ui, &mut b, text)`,
  `radio_value(ui, &mut v, x, text)`. The flag
  that marks a caller-chosen item is `selected(bool)`; the command item
  says `checked(bool)`; a menu checkbox item binds `&mut bool`. Depends on
  D-28, D-30, D-116.

egui idiom: §Selection (`selectable_value`, `radio_value`,
`ComboBox::show_ui`), §Response methods (`mark_changed`).

```rust
let items = [SelectItem::new(Fruit::Apple, "Apple"), SelectItem::new(Fruit::Pear, "Pear").enabled(in_season)];
let r = ui.add(Select::new("fruit", &mut fruit, &items));

```

## T2 · Open state

- Anchored overlays keep their open flag in egui memory and accept an
  optional binding, named after the state: `.open(&mut bool)`; unlike
  egui's `Popup::open(bool)`, it binds rather than forcing one frame,
  which the module docs say. Hover-driven open state (tooltip, the open
  item of menubar and navigation-menu) lives in memory only. Depends on
  D-8, D-4.
- Crate overlays are independent of each other and nest. They form one
  overlay stack: an overlay's parent is the open overlay that contains its
  trigger, and a modal is a root. Closing an overlay closes its
  descendants. Hover overlays (hints: tooltip, hover-card) are on the
  stack for Escape (T3), never for presses, and never return focus.
  *Implementation note:* egui's popup memory keeps one open popup and
  closes a parent on a click in a nested popup's layer, so crate overlays
  keep their own flags (shown with `PopupCloseBehavior::IgnoreClicks`),
  and the parent is the open overlay whose layer holds the trigger
  (`Response::layer_id`; the trigger's `Response` carries no `UiStack`).
  Depends on D-128.
- Dismissal is bits' dismissible layer: a press (pointer down) outside
  the top non-hint overlay closes that overlay only, and the same press
  reaches no other overlay in that pass; a press on an overlay's own
  trigger, or on a hint opened from inside the overlay, is no outside
  press, and the trigger keeps toggling on click; a modal closes on a
  press on its backdrop only while it is the top overlay. A press counts
  also when its release arrives in the same pass. Only a primary-button
  press dismisses (a context-menu trigger's secondary press too), and a
  touch dismisses on its release, not on its press. *Implementation note:*
  "top" for a press is the stack as the pass began; egui clears
  `press_origin` on release, so the position comes from this pass's
  `PointerButton { pressed: true }` event; the modal shell does not use
  `ModalResponse::should_close()` as a whole, which closes on any backdrop
  click. Depends on D-128, D-117.
- The stack's open, close and query operations are public, so an overlay
  built outside the crate nests with crate overlays (Code and shared
  infrastructure); every crate overlay and picker joins it, list pickers
  (select, native-select, combobox) included. Depends on D-128.
- Modals take a required binding as a constructor argument,
  `Dialog::new(id, &mut open)`: a required binding goes into the
  constructor and an optional one into the D-4 setter, as in egui
  (`Checkbox::new(&mut b)` beside `Window::open`). Depends on D-31, D-4.
- Other state by kind: selection and disclosure belong to the caller
  (`&mut`), as upstream's `bind:value` and today's Tabs and Select (egui's
  `CollapsingHeader` keeps disclosure in memory; the crate departs from
  it); panel and view state (sidebar open, sidebar sub-menus, resizable
  layout, calendar month) live in memory with an optional binding;
  transient state (scroll mode, search text, toast queue) lives in memory
  only. Depends on D-32.
- Every memory-owned state is read and driven through associated
  functions keyed by what identifies it: the component's id
  (`Sidebar::toggle(ctx, id)`), or, for an overlay on a caller's trigger,
  hints included, the trigger (`Popover::is_open(ctx, &trigger)`). They
  are named `is_<state>`, `set_<state>` and `toggle`, because the binding
  setter holds the state's own name (`.open`). A trigger gets its
  `expanded` look without a second binding, one pass late because the
  popup id derives from the trigger's `Response`. Initial values only
  where upstream has a default prop; persistence is opt-in. Depends on
  D-33, D-34, D-35.

## T3 · Overlay

- Placement is `.align(RectAlign)` plus `.gap(f32)` on every anchored
  overlay, list pickers included; bits' `alignOffset` values are internal
  constants. A part that depends on placement (an arrow) works for every
  placement the overlay offers. Depends on D-7, D-36.
- Escape closes the top crate overlay only, an open hint first, before
  any crate overlay, `Modal` or egui popup reacts to that press; Escape
  with a modifier counts too. While no crate overlay is open, the crate
  leaves Escape to the app. *Implementation note:* egui's `Popup` and
  `Modal` check Escape inside their own `show`, so the crate consumes the
  key at the start of the pass and marks the top entry of the previous
  pass's stack as closing (Behaviour: a pass-start hook where egui runs
  one, else the first crate overlay call of the pass). Depends on D-38,
  D-128.
- Focus is bits' focus scope. An overlay whose bits content traps focus
  (dialog, alert-dialog, sheet, a popover not opened by hover) moves focus
  in on open, to its first focusable widget (alert-dialog its Cancel
  button; drawer none, as vaul), and Tab and Shift+Tab loop inside it. An
  overlay that does not trap moves focus on open as its primitive does (a
  menu into its panel, where the highlighted item takes the keys; a list
  picker keeps it on its trigger), and Tab closes it and moves on from
  its trigger. Hints move no focus. However an overlay closes (Escape, an
  outside press, a close part, `ui.close()`, the binding), focus returns
  one pass later, if it is gone or inside the closed overlays: to the
  trigger the overlay opened from (for a modal, the widget the opening
  press or key landed on), else to the widget that held focus when it
  opened. Hints never return focus. An overlay's panel is no Tab stop
  (bits `tabindex=-1`). *Implementation note:* egui ignores a focus
  request below the previous pass's top modal, so a modal moves focus in
  on the first pass in which it is the top modal, and its return request
  waits for the first pass in which it is no longer shown. A bare Escape
  clears egui's focus at pass start, so the return target is recorded at
  open; a modal's trigger is the widget egui saw the opening interaction
  on (`interact_widgets`, `Memory::focused`). An egui `Popup` senses
  clicks, which makes its panel focusable. A Tab loop in a non-modal
  overlay consumes Tab at pass start and focuses the next focusable
  widget of the overlay's layer from the previous pass
  (`Memory::set_modal_layer` would also block presses below it). Depends
  on D-39.

  egui paints a focused widget with its `active` (pressed) look whatever
  the modality. So crate widgets get focus on press and on return, and a
  plain egui widget gets focus back only when the overlay was opened or
  closed by keyboard: no pointer action leaves a pressed look the browser
  does not show (P4; maintainer, 2026-10-20).
- Hover overlays share `.open_delay`/`.close_delay` and open on keyboard
  focus. Defaults are upstream's: tooltip 0 (the shadcn provider's
  `delayDuration`), hover-card bits' 0.7 s / 0.3 s; egui's global
  `tooltip_delay` is neither read nor changed. Hint overlays open for
  disabled triggers, action overlays do not. *Implementation note:* the
  crate tooltip is an own popup on its own timer, not egui's tooltip
  machinery. Depends on D-40, D-130, D-82.
- Pickers and menus share one list keyboard model: typeahead (1 s
  buffer), Home/End, loop, skipping disabled items, configured per
  component as its primitive does (PageUp/PageDown move in the select
  list; in a bits menu they act from the panel only, to the first and
  last item). The
  pointer works as bits: a trigger opens on pointer down, and a
  press-drag-release chooses the item under the pointer. Depends on D-45,
  D-116.
- Dismissal behaves as upstream, setters included (Builder shape;
  navigation-menu hover items stay open on an outside touch). Panels on a
  window edge take the crate `Side`; start/end placements use
  `egui::Align` (`Align2` for corners), set by a setter named for what it
  aligns (T7: physical names). Components paint inside their allocation.
  Depends on D-41, D-42, D-43, D-44, D-132.
- An overlay builder on an existing trigger returns
  `Option<InnerResponse<R>>`; a call that draws its own trigger returns
  `InnerResponse<Option<R>>`; a modal returns `Option<InnerResponse<R>>`.
  Depends on D-9, D-31.
- Collision behaviour is upstream's (bits `shift()` with `limitShift`,
  then floating-ui's `flip()` defaults): along its alignment axis an
  anchored overlay shifts to stay in the window, never past its trigger;
  when it still overflows on any side, it tries in order, for a start or
  end alignment, the other alignment, the opposite side, and the opposite
  side with the other alignment (centred: the opposite side only). It
  takes the first that fits, else the one that fits on the side axis with
  the least overflow on the alignment axis, else the one with the least
  total overflow. It never covers its trigger, and a part
  that depends on placement (an arrow) follows the side it took. The chart
  tooltip stays inside the chart. *Implementation note:* egui's
  `RectAlign::find_best_align` takes an alternative only when the whole
  rect fits and `Area::constrain` then clamps onto the trigger, so the
  crate picks the side itself and passes one align. Depends on D-37.

## T8 · Sizing

- Each widget has one width word (D-71 (s1)): a content-sized widget takes
  `.width(f32)`, a widget that fills by default `.max_width(f32)`, never
  both, and no third word. Which one follows from upstream's default
  width (`w-full` fills, `w-fit` or no width is content-sized): text entry
  fills up to `Metrics::field_max_width`; select and native-select are
  `w-fit` and take `.width`; a button takes `.width`. Depends on D-71,
  D-72.
- The width a widget takes is the requested (or default) width, capped to
  the available width (to the window, for a floating overlay), then raised
  to the content minimum; where nothing finite is requested and the
  available width is unbounded (a horizontal `ScrollArea`), it is the
  content minimum. The content minimum is what the widget cannot shrink
  below: its padding plus its fixed parts (chevron, gaps, a thumb's
  length, one glyph for text entry), never 0. `f32::INFINITY` means fill.
  A widget may read the available width to fill or to wrap; any
  arithmetic on it goes through one `layout` helper, which rule 6 of the
  porting standard points to, and a breakpoint read through a second one
  (container width or window width, D-69). A decorative fill takes no
  width setter and never widens an auto-sized parent: in egui's sizing
  pass it reports its minimum. Depends on D-71, D-133.
- Size variants are per-component enums whose middle value is `Default`.
  `size` is a pixel size only on widgets without variants
  (`Spinner::size(f32)`). Depends on D-73, D-74.
- Leaf widgets size themselves before placement (single pass) and never do
  `available_width()` arithmetic of their own (porting standard rule 6). A
  group that needs its children's count, size or ids (button-group,
  toggle-group, input-group, input-otp; radio-group's Tab stop, menu and
  command keys, command group hiding) gets them from one shared item
  registry, which keeps them from the previous pass by id, gives each
  child its position flags (`FIRST`, `LAST`, `NOT_FIRST`, `NOT_LAST`)
  through the parent context (Compound 5), and calls `request_discard`
  when they change. Depends on D-134, D-75.
- Heights resolve as CSS resolves them. `h-full` takes a parent height
  only where the parent has a definite one: a crate container with a
  fixed height or a `.height`. An egui parent (`add_sized`,
  `allocate_ui`) is no definite parent. Against any other parent `h-full`
  is auto, and the recipe or `Metrics` minimum applies (a vertical
  slider's `min-h-40`). `self-stretch` in a
  row is the height of the row's tallest other item, from the previous
  pass (Compound 6); in a column it gives no height. egui's available
  height (the rest of the panel) and `interact_size` are never a parent
  height. A widget that needs a height offers `.height`. Depends on D-76,
  D-77, D-75.
- Text wraps where the browser would wrap it: at the available width, in
  a row as in a column (P4). Label wraps by default and offers
  `.wrap_mode(egui::TextWrapMode)` for another mode; every part drawn
  through Label (a field label, a control's own label) does the same.
  Depends on D-127.

egui idiom: §Widget builders (`add_sized`), §TextEdit (`desired_width`,
`f32::INFINITY`).

```rust

ui.add(Skeleton::new([f32::INFINITY, 16.0]));
```

## Code and shared infrastructure

- These rules cover every function the crate defines, `pub(crate)`
  helpers included: setter and parameter forms, no positional `bool`,
  icons by value, typed parameters instead of parallel arrays. Depends on
  D-2, D-17.
- Code a second component needs is shared, not copied. A port that writes
  what another component already has, or what a component the plan names
  next will need, extracts a crate-private helper in the same PR; a helper
  that exists is called, never restated. A copy is a defect.
- One crate path per concern serves every component, and a component
  that needs a variant extends the path instead of copying it: the text
  path (Looks), the interaction state of a `Response`, a part's opacity,
  the recipe box (fill, border, shadow, focus ring), the press of a pass,
  the overlay stack, the overlay panel frame and its placement, the hover
  timer, the item registry and the generic data item, a group's id, the
  control-plus-label row, the width and breakpoint helpers, the
  roving-focus helper, the list keyboard model.
- Shared code has one owner. Infrastructure several components use,
  generator output and icon slots included, lands in its own step before
  the first component that uses it (design, Stage 3); a port never ships
  a known-wrong look while it waits for one. A part that one component
  draws for another lives in the drawing component's module (a control's
  own label is the `Label` module's); the shared step builds it when
  components of one step both need it.
- A helper is `pub(crate)` unless a port into an app (port-component's
  in-app target, which uses public API only) needs it to meet these
  rules; then it is public, and a public helper struct is
  `#[non_exhaustive]` with a constructor and setters, no public fields. A
  public helper enum is not `#[non_exhaustive]`, also where it grows with
  the crate (`OverlayKind`, `RovingKeys`) (D-131 (b); maintainer,
  2026-10-20).
- A type several components share (`Orientation`, `Side`) lives in its
  own module under `components/` and is re-exported as
  `shadcn_egui::components::<Name>`. Depends on D-6.
- An idle widget costs no heap allocation per frame beyond egui's own:
  accessible names are built inside the `widget_info` closure, styles are
  not cloned per frame, text measured for layout is cached by id, and
  per-widget temporary data leaves egui's memory when it returns to its
  default.
- Snapshot fixtures copy the upstream demo's props (a demo's
  `align="start"` becomes `.align(..)` with start alignment); a fixture
  whose content clips at the window edge is wrong, and so is one that
  sidesteps a case a rule names (a wider window so a tooltip need not
  flip, a fixed height so a separator need not stretch). Per-style
  snapshots show every part a rule styles (a control's own label). Pure
  logic (the overlay stack, the item registry) gets unit tests;
  per-pass mechanisms are tested under both app loops (Behaviour), from
  a root `Ui`, not an `Area` whose first pass is a disabled sizing pass.
  Behaviour tests send input as users and slow frames do: a press and
  its release in one pass, a pointer path as well as an accesskit
  action, a trigger at the window edge, every way an overlay closes.
