# API rules for shadcn-egui components (draft)

Stage 2 draft of the plan `docs/superpowers/plans/2026-10-18-port-all-components.md`.
Every component, the 14 existing ones included, follows these rules. Examples sketch the
target API, not today's code.

## How to use

- The concept decides. The kind templates apply it to each kind of component; the
  conventions add what neither gives. The egui idiom catalogue sections for each kind
  are listed in the implementation notes (17).
- "Behaves and looks as upstream" is defined in `2026-10-18-conformance.md`. How the
  crate builds it in egui is in `2026-10-18-implementation-notes.md`; a note there is
  one way to meet the behaviour, and the behaviour is the requirement.
- A rule answers its question for every function the crate defines, `pub(crate)`
  helpers included. Components named in a rule are examples, never its definition; no
  component is a special case, and its D-entry in `2026-10-18-api-decisions.md` records
  what the rules give it.
- Two clauses that conflict are evidence against one of them or against the structure
  and get a diagnosis, never a silent pick. Where no rule covers a case, derive the
  answer from the concept and the principles, and ask the maintainer before the port
  relies on it.

## Guiding principles

These principles keep their exact wording. The concept applies them; a case that no rule
covers is weighed against them.

- **P1** One consistent API across all components beats completeness:
  when two answers both work, pick the one every component can follow.
- **P2** Use egui's own idiom for the API shape where egui has one
  (builder with `#[inline]` setters, `impl Widget` for leaves,
  `show(ui, closure) -> InnerResponse<R>` for containers, `ui.add_enabled`
  for disabled state, a required binding in the constructor and an
  optional one as a setter), so an egui user can guess the API.
- **P3** Where egui is itself inconsistent, pick one predictable rule.
- **P4** Behaviour and looks follow shadcn upstream at the pins; egui
  decides only the API shape. ("We should not copy egui behavior ... we
  copy shadcn behavior!") The theme may change the look of plain egui
  widgets, not their behaviour.
- **P5** The Rust compiler catches misuse: no stored closures that borrow
  the body's state, no orphan-rule tricks, distinct types where meanings
  differ, so a mix-up does not compile.
- **P6** Before 1.0, correctness beats small breakage. Renames are fine —
  there is no installed base yet. Every break gets a CHANGES.md entry
  that tells users how to upgrade.
- **P7** Minimal dependencies: each new crate is an optional feature and
  needs the maintainer's consent.
- **P8** Decide only what is needed now: crate-wide choices now (the 0.7.0
  cleanup needs them); family-specific choices may wait for the family's
  PR.
- **P9** Colours match upstream exactly; a look that cannot reach the
  exact colour is not acceptable.
- **P10** It must be fun to code against; the principle of least surprise applies.

## The concept

1. **Upstream decides what, egui decides how.** Behaviour, looks and defaults are
   upstream's: the shadcn-svelte component and its bits-ui primitive as the browser runs
   and renders them at the pins (conformance). The API shape is egui's. No egui default,
   layout or setting changes a behaviour, a look or a default. Upstream's composition
   decides which parts exist and their order; egui decides how they are called. A setter
   exists only for an upstream prop, with upstream's default (P8 decides which props a
   port offers now), an upstream part (axiom 4), a binding or initial value (axiom 3), or
   a host setter: a closed list (Conventions) of what the browser gives for free and egui
   must be told, such as an id or a control's own label. Axiom 2 decides only its name
   and shape.
2. **Names come from upstream, the shape from egui.** Components and parts keep
   upstream's names (`Progress`, `card_title`). A function or setter that is the
   one-to-one counterpart of one egui function or setter and behaves as it does takes
   egui's name (`checkbox`, `.gap` as `Popup::gap`); otherwise it takes the crate's
   shared word where one meaning already has one across components (P1:
   `.allow_deselect`, `MenuItem`), and failing that upstream's name (`dropdown_menu` and
   `menubar_menu`, two counterparts of one `menu_button`). Where egui has a counterpart
   (a widget, helper, setter, parameter or type), the crate copies its shape: parameter
   types and order, return type, id semantics. Where egui offers several forms for one
   thing, the crate mirrors the one P2 names: an optional binding is a setter that takes
   `&mut`, as `Window::open(&mut bool)`, not `Popup::open(bool)` or `Popup::open_bool`,
   named by this axiom (accordion `.value`, upstream's prop). A crate type that mirrors
   an egui type offers the subset the crate needs, each member as egui has it unless a
   rule names a P3 pick.
3. **State goes to whoever needs it.** Where the egui counterpart leaves a state to the
   caller, the crate does too: a modal draws while the app's own flag is set and reports
   `should_close()`, as egui's `Modal`. Otherwise a binding is required when the app
   acts on the value, because the value is what the app uses the component for (a value
   control such as a checkbox, switch, toggle or slider; a selection; the tab whose
   content the caller draws). A required binding is a constructor argument, as egui's
   `Checkbox::new(&mut b)`. State the component changes and uses itself, and that
   upstream lets a caller bind or drive, lives in egui memory with an optional binding
   named after the state (axiom 2) and an initial value `.default_<state>(..)` (Svelte's
   unbound bindable prop): an anchored overlay's open flag, accordion disclosure (as
   egui's `CollapsingHeader`). An API object counts as a binding (carousel's `setApi`,
   paneforge's `this`). State upstream lets a caller neither bind nor drive lives in
   memory only: scroll mode, the toast queue.
4. **A component is built from a few kinds, and all are called one way.** Leaf,
   container, anchored overlay, modal, data item, immediate item, handle, part, service
   (Kind templates). Every component and every part is a builder `X::new(required)` with
   setters. A leaf is placed with `ui.add(x)`, anything else with `x.show(ui, |ui| ..)`;
   an overlay uses the `Ui` for context and layer only (P3: egui's targets differ), and
   a call that places nothing (a toast) shows on the `&Context`, as `Window::show(ctx)`.
   A free function is only a shortcut for one builder call. Classifying a component, or
   each of its upstream parts, gives its state form, id form and shortcut. Where
   upstream's API lets the caller arrange the parts (groups, separators), the root is a
   handle if it holds state about the parts the caller arranges (which is open or
   active, values across slots, roving focus), else a container; otherwise the parts
   collapse into one widget (checkbox indicator, slider track and thumb, calendar grid).
5. **Context flows down.** A crate widget inside a crate parent takes the parent's
   context by itself (recipe, size, orientation, `invalid`, position in a group): a
   button in a button-group, kbd in a tooltip, an item in a menu. No per-parent widget
   type and no extra argument. Where the child has a setter of its own (axiom 1), the
   caller's explicit call overrides the context; a look the context gives changes
   through an app variant (axiom 8).
6. **Misuse does not compile.** Distinct meanings get distinct types; a setter that only
   one mode understands lives on that mode's type; content a mode needs is a constructor
   argument, never a flag. Where the compiler cannot catch a misuse, a `debug_assert!`
   names it. Nothing fails silently: anything that compiles has its effect. A value of an
   egui type is honoured in all it carries, as the egui widget that takes it does (image
   and text atoms, `atom_grow`, `RichText` attributes); what the crate cannot honour
   (`Atom::custom`, a width on an icon-only select) fails a `debug_assert!`.
7. **One shape per concern.** A concern several components share (text, icons, ids, open
   state, sizing, orientation, roving focus) has one API shape that every component
   uses, built on one crate path (implementation notes 1).
8. **Looks are central.** An app changes a component's look by defining app variants and
   app sizes once in its theme, from built-in ones, and naming them at the call,
   everywhere. A look a demo gives with a class is an app variant; a style function
   upstream exports for another part (`navigationMenuTriggerStyle`, `buttonVariants` on a
   trigger) is a built-in variant of the receiving part. A value a class gives is a look,
   motion included (`duration-100`, `zoom-in-95`); a delay a prop gives (`openDelay`) is
   behaviour. A call sets a look only through upstream's props (`.variant(..)`,
   `.size(..)`, toggle-group `.spacing(f32)`); content attributes stay content (axiom 6).
   The style stays the single source of every visual value: an app variant sets what its
   edit names and keeps the rest of its base, in every state, mode and style (App
   variants).

## Kind templates

| Kind | Call | State | Id | Shortcut |
|---|---|---|---|---|
| Leaf | `ui.add(X::new(req).opt(..))` | none, or a caller binding in `new` | auto | `x(ui, ..)` |
| Container | `X::new(..).opt(..).show(ui, \|ui\| ..)` | none, or memory + optional binding, held for the call | scoped: fixed salt or label | none |
| Anchored overlay | `X::new(&resp).opt(..).show(ui, \|ui\| ..)` | memory + `.open(&mut bool)` | from the trigger | egui's counterpart only |
| Modal | `X::new(id_salt).show(ui, \|ui\| ..)` while the app's flag is set | the app's flag | global | none |
| Data item | `XItem::new(value, content).opt(..)`, stored by the widget | plain `T` value | index, or value if items reorder | none; `(value, text)` converts |
| Immediate item | `ui.add(XItem::new(&mut v, x, text))` | carries the binding | auto | `radio_value(ui, &mut v, x, text)` |
| Handle | `X::new(..).show(ui, \|h\| { h.add(XPart::new(..)); })` | parent holds it | from the parent | none |
| Part | `ui.add(XPart::new(..))`, `XPart::new(..).show(ui, \|ui\| ..)` | none | auto | `x_part(ui, ..)`; in a handle its method |
| Service | `Toaster::new().show(ui)`; `Toast::new(text).show(ctx)` | memory only | global | `toast(ctx, text)` |

**Every builder.** Setters chain as `fn x(mut self, ..) -> Self`; `new` and setters are
`#[inline]`; a `new()` without arguments comes with a `Default` impl; the type carries
`#[must_use]` with egui's message. `ui.add(x)` returns the `Response`, `show` an
`InnerResponse<R>` or the egui counterpart's type (`Option<InnerResponse<R>>` as
`Popup::show`; `menu_button`'s `InnerResponse<Option<R>>` where the call draws its
trigger). With more to return, a leaf also has `show(ui)`, as `TextEdit::show`, and the
call returns the mirrored egui widget's output type (`TextEditOutput`), else its own
`XOutput` with a `response` field, plus `inner` where a closure runs.

**Ids.** A component whose egui counterpart requires an id takes `id_salt: impl Hash` in
its constructor, also where egui takes an `Id` (P3: `Modal::new` and `Area::new` take an
`Id`, `ComboBox::from_id_salt` a salt): modals, the sidebar on `Panel`, select and
native-select like `ComboBox`, chart on `egui_plot::Plot`. Any other component offers
`.id_salt(impl Hash)` exactly when it keeps state across passes beyond egui's own
per-widget focus and animation state, or wraps an egui widget that offers one. Floating,
panel and app-level ids are global (`Id::new(salt)`, as `Panel::left(id)`); in-flow ids
are scoped (`ui.make_persistent_id(salt)`, as `TextEdit::id_salt`).

- A component with a state type defaults, as egui's stateful containers, to a fixed
  salt per component (`"accordion"`, as `ScrollArea`'s `"scroll_area"`) or to its label
  (as `CollapsingHeader`); any other keeps the default of the egui widget it wraps, or
  the auto id for transient state (a caret, an active cell), as `TextEdit`.
- Its `Response` carries the id; an output type has an `id` field (`ScrollAreaOutput`).
- Two components with one id share their state; docs say two in a `Ui` need `.id_salt`.

**Memory-owned state.** A state in memory with an optional binding (axiom 3) has one
state type `XState` (`PopoverState`, `CarouselState`) for code that reads or changes it
at run time; state in memory only has none, and no other type takes the suffix.

- `XState` has `CollapsingState`'s members, named after the state: `load`,
  `load_with_default_<state>`, `store`, `remove`, `id`, the getter (`is_open()`,
  `index()`) and `set_<state>`. `load` takes the id the component reports (`None` before
  the first pass). P3 picks: an overlay on a caller's trigger loads by the drawn trigger
  (`PopoverState::load(ctx, &trigger)`), and `store` requests a repaint, so `toggle()`
  takes no `Ui`.
- A set binding is the initial value and wins when it and memory both changed; a value
  stored through `XState` reaches it on the next call. `.default_<state>` applies only
  without a binding, while memory holds no value, as egui's
  `CollapsingHeader::open(Some(..))` wins over `default_open`; setting both fails a
  `debug_assert!` (axiom 6).
- Nothing persists across restarts (axiom 1); an app keeps state through the binding.
  An opt-in upstream offers (resizable `autoSaveId`) exists only with the crate's
  `persistence` feature, which turns on egui's, so it never compiles without effect.

**Shortcuts.** A shortcut does exactly what one builder call does and returns what it
returns. It takes the builder's value form and content only, never a variant (no
`separator_vertical`), and an id exactly when the builder requires one. Its name follows
axiom 2, its form egui's sugar: the `Ui`, then egui's parameter order (`switch(ui, &mut
b, text)`, `card_footer(ui, |ui| ..)`). One on a caller's trigger takes the trigger in
place of the `Ui`, as egui's `Response` methods do, by value where it returns it.

### Leaf

A widget that draws itself and holds no caller content: display leaves (badge, kbd,
separator, progress) and value leaves (checkbox, switch, toggle, slider, input, select,
native-select, toggle-group, pagination, calendar).

- A value leaf binds the caller's value in its constructor. It writes the binding only
  in response to user input, then calls `mark_changed()`; the caller reads `changed()`.
- Shortcut when the constructor holds all a common call needs, and for every value
  picker over a list or a range; otherwise none.

```rust
ui.add_enabled(ready, Button::new("Save").variant(ButtonVariant::Outline).icon(icons.check));
if switch(ui, &mut self.notify, "Email notifications").changed() { self.save(); }
let items = [SelectItem::new(Fruit::Apple, "Apple"), SelectItem::new(Fruit::Pear, "Pear").enabled(in_season)];
select(ui, "fruit", &mut fruit, &items);
```

### Container

A component that lays out caller content in its own surface in the flow of a `Ui`: card,
alert, field, breadcrumb, accordion item, collapsible, scroll area, sidebar.

- A mirrored type keeps egui's `show_*` variants (`ScrollArea::show_rows`).
- Parts that only render data are setters on the root (`.title`, `.description`, media,
  bubble reactions); the parts (`card_title(ui, ..)`) stay for custom layouts.
- A component whose surface encloses the caller's content holds a set binding for the
  call, as `Window::open` does, so a content closure that reaches the same owner does
  not compile (popover, accordion, collapsible); its docs show egui's local-copy idiom
  (`let mut open = self.open; …; self.open = open;`).
- Where upstream demos use both setter content and free content, one type offers
  `ui.add(X::new(req))` and `X::new(req).show(ui, |ui| ..)`, with one `new` for both.

```rust
Card::new().title("Create project").show(ui, |ui| {
    card_footer(ui, |ui| { if ui.add(Button::new("Deploy")).clicked() { deploy(); } });
});
```

### Anchored overlay

A panel placed against a trigger, on the crate overlay stack: popover, tooltip,
hover-card, menus, a picker's list.

- `new` takes the trigger by `&Response`, as `Popup::from_response`; `X::button(impl
  IntoAtoms)` draws its own, as egui's `MenuButton::new`. `.id_salt` tells several
  overlays on one trigger apart; it does not make the overlay reachable without one.
- Placement on every anchored overlay, list pickers included: `.align(RectAlign)` and
  `.gap(f32)`. Hover overlays offer the delays upstream offers (axiom 1): `.open_delay`
  for `delayDuration` and `openDelay`, `.close_delay` for `closeDelay`, `.skip_delay`
  for `skipDelayDuration`.
- Shortcuts exist only where egui has the helper: `dropdown_menu`, `menubar_menu`,
  `context_menu`, `tooltip` (`menu_button`, `Response::context_menu`, `on_hover_text`).

```rust
Popover::new(&resp).open(&mut self.popover_open).show(ui, |ui| { ui.label("Hi"); });
let r = tooltip(ui.add(Button::new("?")), "Help");
let r = dropdown_menu(ui, "Options", |ui| { ui.add(MenuItem::new("Copy")) });
```

### Modal

A floating overlay with a backdrop: dialog, alert-dialog, sheet, drawer, command dialog.
It takes no open flag (axiom 3). `XOutput<R>` mirrors `ModalResponse` (`response`,
`inner`, `should_close()`) with the crate's dismissal (conformance 5.2) and is
`#[must_use]`. `should_close()` turns true once the exit motion has run (conformance 7),
so the app clears its flag on it, and content closes the modal with `ui.close()`.

```rust
if self.confirm_open {
    let out = AlertDialog::new("confirm").title("Delete file?").show(ui, |ui| {
        alert_dialog_footer(ui, |ui| {
            alert_dialog_cancel(ui, "Cancel");
            let delete = alert_dialog_action(ui, "Delete").clicked();
            if delete { ui.close(); }
            delete
        }).inner
    });
    if out.inner { self.delete_file(); }
    if out.should_close() { self.confirm_open = false; }
}
```

### Data item

An item the widget needs while it is closed or before it paints it: trigger text and
typeahead (select, native-select), toggle-group items, tab triggers.

- Every item list, in the builder and the shortcut, takes `impl IntoIterator` of
  anything that converts into the item type: item values, `(value, text)` tuples, by
  value or by reference; a list of plain values takes `impl IntoIterator<Item = T>`.
- A shared item type (the generic data item) serves only where all its setters work;
  otherwise the component has its own type.

### Immediate item

A leaf called inside its parent's closure that carries the binding itself, where items
can have arbitrary neighbours: a radio item, a menu's checkbox and radio items. It keeps
the egui counterpart's parameters (Selection). An item that binds nothing (a plain menu
item) is a part.

### Handle

Passed to the closure where the root holds state about the parts the caller arranges
(axiom 4): tabs, accordion, input-otp, navigation-menu, message-scroller, table.

- The handle derefs to the `Ui` it wraps, so parts go in as into any `Ui`
  (`h.add(TabsList::new(..))`, `AccordionItem::new(..).show(h, |ui| ..)`) and read the
  handle's state from it (axiom 5). The handle's methods are its parts' only shortcuts,
  named after the part (`t.list(..)`; `item` only for an `Item` part). An item value
  and its text are positional (`acc.item(Faq::Shipping, "Shipping?", |ui| ..)`).
- Repeated uniform children come as a count plus an index closure (carousel slides,
  resizable panes).

```rust
Tabs::new(&mut self.tab).show(ui, |t| t.list([(Tab::Account, "Account"), (Tab::Password, "Password")]));
TabsContent::new().show(ui, |ui| match self.tab {
    Tab::Account => self.account_ui(ui),
    Tab::Password => self.password_ui(ui),
});
```

### Part

An upstream part inside its root, as upstream nests it, so context flows down (axiom
5): a leaf (separator, label, heading) or a container (footer, header action), with a
shortcut. No part is called beside its root, except app content chosen by the root's
bound value (tabs content): it takes no context and comes after the root, as egui's
`selectable_value` then `match`, so its closure can borrow the app (P10).

- Parts are called in upstream's source order, which is also Tab and reading order. A
  part upstream places before the content (a header action, `card_action`) is called
  first, a footer (`card_footer`, `dialog_footer`) last; a part out of order fails a
  `debug_assert!`. Footers keep upstream's direction, and the caller nests a layout
  inside.
- Side slots (item and attachment actions) are the closure itself, because the main
  content there is setter data.
- A group's label is a heading part (`menu_label`), except where the group is a data
  list or hides when none of its items is shown; then the group carries its label.
- What a container must know about a part or child before it draws (an action's size, a
  child count, a position) it takes from the previous pass (conformance 3.2).

### Service

An app-level facility with no place in the layout: sonner's toaster, one per app,
`Toaster::new()` on a fixed global id, whose `.show(ui)` places it and returns events. A
toast places nothing, so it shows on the `&Context` (axiom 4) and `App::logic` can raise
one: `Toast::new(text).show(ctx) -> ToastId`, shortcut `toast(ctx, text)`.

### Mapping upstream parts and events

- An upstream `on<Event>` prop becomes a `Response` query where egui has one
  (`changed()`, `clicked()`), else an output field (`InputOtpOutput { completed, .. }`).
- An upstream `Close` part without a look of its own becomes `ui.close()`. A part that
  is a styled button takes upstream's props, default variant and close behaviour:
  `alert_dialog_cancel(ui, text)` is an outline button that closes.
- A `Provider` part's settings become the defaults or root state of what it configures:
  the tooltip provider's delay is the tooltip's default, the sidebar provider `Sidebar`.

## Conventions

### Enums and flags

- Every variant and size enum of a component derives `Clone, Copy, Debug, Default,
  PartialEq, Eq`, with upstream's default as `#[default]`. Data-carrying enums derive
  what their fields allow. Shared enums (`Orientation`, `Side`) have no `Default`; their
  default is per component.
- Variant and size enums are `#[non_exhaustive]`; closed sets and public helper enums
  are not, also where they grow with the crate (`OverlayKind`, `RovingKeys`).
- Exclusive states with three or more values are enums.
- A flag setter takes a `bool`: `.invalid(bool)`, `.expanded(bool)`. A flag that
  defaults to `true` keeps its positive name and is called with `false`. No positional
  `bool` parameters.
- A setter without an argument exists only as a shortcut for one value of an enum
  setter (`.vertical()`, Sizing).
- The host setters (axiom 1) are these, and a new one needs the maintainer: `.id_salt`
  (Ids); `.label` (Selection); `.wrap_mode` on Label and what it draws; `.sense`, `.link`
  (State flags); `.enabled` (Disabled); `.width`, `.desired_width`, `.height` (Sizing).

### App variants

- Every variant enum and every size enum `X` names app cases by `const fn app(name:
  &'static str) -> AppVariant<X>`. `AppVariant<X>` is `Copy` and `Eq`, and `impl
  From<AppVariant<X>> for X` lets the setter take it (`.variant(impl Into<X>)`). A
  component without a variant enum gets `XVariant` with the one built-in case `Default`
  and a `.variant(..)` setter; one without a size enum has no app sizes, and its app
  variants carry its sizes.
- The theme defines each app variant once, from a built-in one: `Theme::variant(app:
  AppVariant<V>, base: V, |r, style| ..)`, and `Theme::size` for a size, so a swapped
  pair does not compile. The edit is a `fn` that captures nothing and gets copies of the
  base's recipes and the `StyleName`, so a look may differ per style; the theme keeps
  base and edit and builds for its current style, so an app variant holds in every
  style. A theme holds both palettes, `Theme::apply` installs both looks, and the crate
  follows egui's `ctx.set_theme(ThemePreference)`; both modes share the app variants.
- The edit gets `&mut XRecipes` for every component: one `Recipe` field per upstream
  part the variant reaches, named after its `data-slot` in snake case, a pseudo-element
  after its slot plus the pseudo-element (`TabsRecipes { tabs_list, tabs_trigger,
  tabs_trigger_after }`, the last the line under the active tab). The struct is
  `#[non_exhaustive]`, so a later part breaks no edit; each component has a test that
  compiles one edit.
- An edit states values per state, as a class list does: `prop.set(v)` replaces the
  unconditional value and keeps the base's state rules; `prop.on(state, v)` replaces the
  base's rules for that state, as tailwind-merge does; `recipe.recolor(from, to)` swaps a
  colour role in every value and rule of the part, opacity kept.
- App colours (a light and dark pair on the theme) give app variants colours no palette
  role has. Docs and examples name them and app variants through constants (`const
  BRAND: Role = Role::custom("brand");`), so a misspelling does not compile; a name the
  theme does not define fails a `debug_assert!` and draws as the `Default` variant.

```rust
const DANGER_GHOST: AppVariant<ButtonVariant> = ButtonVariant::app("danger-ghost");
const DANGER_OUTLINE: AppVariant<ButtonVariant> = ButtonVariant::app("danger-outline");
let theme = Theme::vega()
    .variant(DANGER_GHOST, ButtonVariant::Ghost, |r, _style| {
        r.button.text.set(Paint::Role(Role::Destructive, 1.0)); // Ghost's hover colours stay
    })
    .variant(DANGER_OUTLINE, ButtonVariant::Outline, |r, _| r.button.recolor(Role::Foreground, Role::Destructive));
ui.add(Button::new("Delete").variant(DANGER_GHOST));
```

### Modes

- `new` builds the common mode; each other mode or alternative content has a named
  constructor (`Accordion::multiple`, `Kbd::icon_only`, `DropdownMenu::button`).
  `from_*` names an alternative input form (`Progress::from_value`,
  `Pagination::from_count`), as egui's `ComboBox::from_label`.
- Icon-only content is a mode on every component with text content: `X::icon_only(..,
  icon, name)`, with `name` as the accessible name. Where upstream spells it as size
  variants, the mode picks the icon variant of the chosen size, and the size enum keeps
  the text sizes. An overlay's icon trigger is the caller's own trigger
  (`DropdownMenu::new(&ui.add(Button::icon_only(..)))`).

### Parameter types

- Text takes the type that fits what the component does with it, on a builder and on a
  data item alike: `impl Into<String>` when it also reads the text as data (filter,
  typeahead, comparison, an accessible name); `impl IntoAtoms` for one row that does not
  wrap, with icon slots (button, badge, kbd, toggle, toggle-group item, tab trigger),
  clickable or not; `impl Into<WidgetText>` for text that wraps (titles, descriptions,
  an accordion trigger), except a choice control's own label (Selection).
- A pick list's empty text is `placeholder(impl Into<WidgetText>)`.
- Icons by value (`Icon` is `Copy`); colours as `impl Into<Color32>`; typed parameters,
  not parallel arrays; a predicate prop is a `fn` pointer, borrowing nothing (P5) and
  needing no regex (P7): input-otp `pattern: fn(char) -> bool`.
- Units are egui's: `f32` seconds (`.open_delay(0.7)`) and points; a Tailwind step is 4
  points (`spacing={1}` is `.spacing(4.0)`, `max-w-sm` is `.desired_width(384.0)`).

### Media and icons

- Media slots are `.icon(Icon)`, `.image(impl Into<ImageSource>)` and `.media(closure)`.
  Icon slots that may show a spinner take `impl Into<Glyph>`.
- Crate widgets and data items show icons through typed `.icon` slots, painted in the
  recipe's state colour. An `IconAtom` in a crate widget's content takes the same
  colour, unless the caller gave it one (conformance 2.3). egui hosts get crate icons
  through `IconAtom(icon)`, an image atom tinted with a caller colour or the text colour.
- `IconSlots` (`#[non_exhaustive]`) names a slot per shape, plus a role-named slot where
  an icon library uses another icon for one role than for the shared shape
  (`calendar_prev`, `select_trigger`); a slot whose meaning changes gets a new name.

### Disabled

- Disabled state comes from the `Ui` (`ui.add_enabled`, `add_enabled_ui`); a widget
  reads it from its `Response` in one place.
- A component also takes `.enabled(bool)` exactly when upstream gives it a `disabled`
  prop whose effect a disabled `Ui` does not reproduce: the prop leaves part of what the
  component holds interactive (an accordion item's trigger, not the caller's panel), or
  the component has no `Ui` a caller could disable (a data item, an overlay on a
  caller's trigger).
- `.enabled(false)` does only what the prop does; closure items take `add_enabled_ui`.

### Selection

- A choice binds `&mut T` with `T: PartialEq` (+ `Clone` where the widget holds a list);
  multiple selection binds `&mut Vec<T>`. Domain values stay domain types (`f32`,
  `Date`, a 1-based page). A component that owns and validates the answers itself keeps
  them in its own type (questionnaire: indices in `&mut QuestionnaireAnswers`).
- A choice that can be empty binds `&mut Option<T>`, by a mode constructor where the
  widget also binds `&mut T` (`Select::optional(id, &mut Option<T>, items)`); its data
  items stay plain `T`, its immediate items take the binding's type, as egui's
  `radio_value(ui, &mut plan, Some(Plan::Free), ..)`. A widget that can clear its value
  by itself is empty-capable only (toggle-group, accordion and calendar single).
- Deselect by a second click has the setter `.allow_deselect(bool)` (select
  `allowDeselect`, calendar `preventDeselect` inverted), only where upstream has the
  prop and the binding can be empty.
- A caller-chosen item's flag is `selected(bool)`, as egui's `Button::selected`.
- Choice controls (checkbox, switch, radio item) take an optional own label,
  `.label(impl IntoAtoms)` as egui's `Checkbox`; its text atom wraps (conformance 4.5).

### Sizing, orientation, placement, scrolling

- A dimension the style sets is a look (axiom 8). Where the style leaves the extent to
  the parent (`w-full`, `w-fit`, no width), the caller's `Ui` gives it: a widget that
  fills takes the `Ui`'s width, and a content-sized widget fills a justified layout
  (`ui.add_sized`), as egui's `Button`.
- A width setter exists only for an extent from where the widget sits, as a host setter
  that mirrors an egui setter, and takes egui's name, one word per widget: `.width(f32)`
  on a content-sized widget, as `ComboBox::width`, `.desired_width(f32)` on one that
  fills, as `TextEdit`'s (conformance 3.1). `f32::INFINITY` means fill; a decorative fill
  takes none. A height setter exists on the same terms (chart as `Plot::height`).
- Size variants are per-component enums whose middle value is `Default`. `size` is a
  pixel size only where it mirrors egui's (`Spinner::size(f32)`).
- One crate `Orientation { Horizontal, Vertical }`, set with `.orientation(..)` or the
  `.vertical()` shortcut, as egui's Slider.
- Panels on a window edge take the crate `Side`. Start and end placements use
  `egui::Align` (`Align2` for corners), set by a setter named for what it aligns. The
  crate is LTR only; placement types are egui's, whose names are physical.
- Where upstream makes a responsive mode an opt-in (field's `orientation="responsive"`),
  the crate does too (`.responsive(bool)`). Modes shadcn neither styles nor demos are
  left out.
- Every crate component that scrolls uses the crate `ScrollArea`, and so do demos and
  docs where upstream scrolls.

### State flags and validation

- A `State` flag exists for each state a recipe styles, and only then (porting standard
  rules 2 and 3); its meaning is the upstream attribute it stands for (conformance 2.9).
- `invalid` exists where a recipe styles `aria-invalid`; a group or a Field passes it to
  the widgets inside. Validation is `.invalid(bool)` plus `.error(text)`.
- Display widgets become clickable with `.sense(Sense)`; `.link(bool)` gives the link
  look and role (conformance 4.1).

### Names and public surface

- Part types and their shortcuts carry the component prefix plus upstream's part name
  (`card_title`, `TabsTrigger`, `SelectItem`); a part several components share takes
  the shared word (axiom 2: `MenuItem`, `MenuSeparator` in dropdown, context menu and
  menubar). A helper type with another meaning than an egui type does not take its name.
- A public name that differs from upstream's carries `#[doc(alias = "<upstream name>")]`,
  so rustdoc search finds it (`hint_text` for `placeholder`, `open_delay` for
  `delayDuration`).
- A helper is `pub(crate)` unless a port into an app (port-component's in-app target,
  public API only) needs it to meet these rules; then a public helper struct is
  `#[non_exhaustive]` with a constructor and setters, no public fields.
- No `#[deprecated]` aliases or forwards before 1.0: a rename or removal breaks at once,
  and CHANGES.md gives the upgrade step.
