# API rules for shadcn-egui components (draft)

Stage 2 draft of the plan `docs/superpowers/plans/2026-10-18-port-all-components.md`.
Every component, the 14 existing ones included, follows these rules. Examples sketch the
target API, not today's code.

## How to use

- The concept decides. The kind templates apply it to each kind of component; the
  conventions add what neither gives. The egui idiom catalogue sections for each kind
  are listed in the implementation notes (17).
- "Behaves and looks as upstream" is defined in `2026-10-18-conformance.md`. How the
  crate builds it in egui is in `2026-10-18-implementation-notes.md`; a note there is
  one way to meet the behaviour, and the behaviour is the requirement.
- A rule answers its question for every component. Components named in a rule are
  examples, never its definition. No component is a special case of a rule; its D-entry
  in `2026-10-18-api-decisions.md` records what the rule gives it.
- The rules cover every function the crate defines, `pub(crate)` helpers included.
- Two clauses that conflict are evidence against one of them or against the structure;
  the conflict gets a diagnosis, never a silent pick.
- Where no rule covers a case, derive the answer from the concept and the principles,
  and ask the maintainer before the port relies on it.

## Guiding principles

These principles keep their exact wording. The concept applies them; a case that no rule
covers is weighed against them.

- **P1** One consistent API across all components beats completeness:
  when two answers both work, pick the one every component can follow.
- **P2** Use egui's own idiom for the API shape where egui has one
  (builder with `#[inline]` setters, `impl Widget` for leaves,
  `show(ui, closure) -> InnerResponse<R>` for containers, `ui.add_enabled`
  for disabled state, a required binding in the constructor and an
  optional one as a setter), so an egui user can guess the API.
- **P3** Where egui is itself inconsistent, pick one predictable rule.
- **P4** Behaviour and looks follow shadcn upstream at the pins; egui
  decides only the API shape. ("We should not copy egui behavior ... we
  copy shadcn behavior!") The theme may change the look of plain egui
  widgets, not their behaviour.
- **P5** The Rust compiler catches misuse: no stored closures that borrow
  the body's state, no orphan-rule tricks, distinct types where meanings
  differ, so a mix-up does not compile.
- **P6** Before 1.0, correctness beats small breakage. Renames are fine —
  there is no installed base yet. Every break gets a CHANGES.md entry
  that tells users how to upgrade.
- **P7** Minimal dependencies: each new crate is an optional feature and
  needs the maintainer's consent.
- **P8** Decide only what is needed now: crate-wide choices now (the 0.7.0
  cleanup needs them); family-specific choices may wait for the family's
  PR.
- **P9** Colours match upstream exactly; a look that cannot reach the
  exact colour is not acceptable.
- **P10** It must be fun to code against; the principle of least surprise applies.

## The concept

1. **Upstream decides what, egui decides how.** Behaviour, looks and defaults are
   upstream's: the shadcn-svelte component and its bits-ui primitive as the browser runs
   and renders them at the pins (conformance). The API shape is egui's. No egui default,
   layout or setting changes a behaviour, a look or a default. Upstream's composition
   decides which parts exist and their order; egui decides how they are called. A setter
   exists only for an upstream prop, with upstream's default (P8 decides which props a
   port offers now), an upstream part (axiom 4), a binding or initial value (axiom 3), or
   a host setter: a closed list (Conventions) of what the browser gives for free and egui
   must be told, such as an id or a control's own label. Axiom 2 decides only its name
   and shape.
2. **Names come from upstream, the shape from egui.** Components and parts keep
   upstream's names (`Progress`, `card_title`). A function or setter that is the
   one-to-one counterpart of one egui function or setter and behaves as it does takes
   egui's name (`checkbox`, `radio_value`, `toggle_value`, `.desired_width`, `.gap` as
   `Popup::gap`); otherwise it takes the crate's shared word where one meaning already has
   one across components (P1: `.allow_deselect`, `checked`, `.search`), and failing that
   upstream's name (`dropdown_menu` and `menubar_menu`, two counterparts of one
   `menu_button`; `tooltip`, whose timer and popup are not `on_hover_text`'s). Where egui
   has a counterpart (a widget, helper, setter, parameter or type), the crate copies
   its shape: parameter types and order, return type, id semantics. Where egui offers
   several forms for one thing, the crate mirrors the one P2 names: an optional binding
   is a setter named after the state, as `Window::open(&mut bool)`, not
   `Popup::open(bool)` or `Popup::open_bool`. A crate type that mirrors an egui type
   offers the subset the crate needs, each member as egui has it.
3. **State goes to whoever needs it.** Where the egui counterpart leaves a state to the
   caller, the crate does too: a modal draws while the app's own flag is set and reports
   `should_close()`, as egui's `Modal`. Otherwise a binding is required when the app acts
   on the value, because the value is what the app uses the component for (a value
   control such as a checkbox, switch, toggle or slider; a selection; the tab whose
   content the caller draws). A required binding is a constructor argument, as egui's
   `Checkbox::new(&mut b)`. State the component changes and uses itself, and that
   upstream lets a caller bind or drive, lives in egui memory with an optional binding
   named after the state and an initial value `.default_<state>(..)` (in Svelte an
   unbound bindable prop is the initial value): an anchored overlay's open flag,
   accordion disclosure (as egui's `CollapsingHeader`). A set binding wins over
   `.default_<state>`. An API object counts as a binding (carousel's `setApi`,
   paneforge's `this`). State upstream lets a caller neither bind nor drive lives in
   memory only: scroll mode, the toast queue. Memory-owned state persists as egui's own
   does (Memory-owned state).
4. **A component is built from a few kinds.** Leaf, container, anchored overlay, modal,
   data item, immediate item, handle, part fn, service (Kind templates). Classifying a
   component, or each of its upstream parts, gives its signature, return type, state
   form, id form and shortcut. Where upstream's API lets the caller arrange the parts
   (groups, separators), the root is a handle; otherwise the parts collapse into one
   widget (checkbox indicator, slider track and thumb, calendar grid).
5. **Context flows down.** A crate widget inside a crate parent takes the parent's
   context by itself (recipe, size, orientation, `invalid`, position in a group): a
   button in a button-group, kbd in a tooltip, an item in a menu, bubble alignment from
   message. No per-parent widget type and no extra argument. Where the child has a setter
   of its own (axiom 1), the caller's explicit call overrides the context; a look the
   context gives changes through an app variant (axiom 8).
6. **Misuse does not compile.** Distinct meanings get distinct types; a setter that only
   one mode understands lives on that mode's type; content a mode needs is a constructor
   argument, never a flag. Where the compiler cannot catch a misuse, a `debug_assert!`
   names it. Nothing fails silently: anything that compiles has its effect. A value of an
   egui type is honoured in all it carries, as the egui widget that takes it does (image
   and text atoms, `atom_grow`, `RichText` attributes); what the crate cannot honour
   (`Atom::custom`, a width on an icon-only select) fails a `debug_assert!`.
7. **One shape per concern.** A concern several components share (text, icons, ids, open
   state, sizing, orientation, roving focus) has one API shape that every component
   uses, built on one crate path (implementation notes 1).
8. **Looks are central.** An app changes a component's look by defining app variants and
   app sizes once in its theme, from built-in ones, and naming them at the call,
   everywhere. A look a demo gives with a class is an app variant; a style function
   upstream exports for another part (`navigationMenuTriggerStyle`, `buttonVariants` on a
   trigger) is a built-in variant of the receiving part. A call sets a look only through
   upstream's props (`.variant(..)`, `.size(..)`, toggle-group `.spacing(f32)`); content
   attributes stay content (axiom 6). The style stays the single source of every visual
   value: an app variant sets what its edit names and keeps the rest of its base, in
   every state, mode and style (App variants). Extent is not a look (Sizing).

## Kind templates

| Kind | Signature | Returns | State | Id | Shortcut |
|---|---|---|---|---|---|
| Leaf | `ui.add(X::new(req).opt(..))` | `Response`; `show(ui) -> XOutput` for more | none, or a caller binding in `new` | auto | `x(ui, ..) -> Response` |
| Container | `X::new(..).opt(..).show(ui, \|ui\| ..)` | `InnerResponse<R>` | none, or memory + optional binding, held for the call | scoped: fixed salt or label | none |
| Anchored overlay | `X::new(&resp).opt(..).show(\|ui\| ..)` | `Option<InnerResponse<R>>` | memory + `.open(&mut bool)` | from the trigger | egui's counterpart only |
| Modal | `X::new(id_salt).show(ctx, \|ui\| ..)` while the app's flag is set | `XOutput<R>` with `should_close()` | the app's flag | global | none |
| Data item | `XItem::new(value, content).opt(..)` | stored by the widget | plain `T` value | index, or value if items reorder | none; `(value, text)` converts |
| Immediate item | `radio_value(ui, &mut v, x, text)` | `Response` | carries the binding | auto | is the call |
| Handle | `X::new(..).show(ui, \|h\| { h.link(..); })` | `InnerResponse<R>`; each method its part's | parent holds it | from the parent | none |
| Part fn | `x_part(ui, ..)`, `x_part(ui, \|ui\| ..)` | `Response`, `InnerResponse<R>` | none | auto | is the call |
| Service | `toast(ctx, ..) -> ToastId`; `Toaster::show(ctx)` | handle; events | memory only | global | is the call |

**Every builder.** `new(..)` takes the required data; options are chained setters `fn
x(mut self, ..) -> Self`; `new` and setters are `#[inline]`; a `new()` without arguments
comes with a `Default` impl; the type carries `#[must_use]` with egui's message. Where
there is more to return than egui's form gives, a component that mirrors an egui widget
returns that widget's output type (`TextEditOutput`, `CollapsingResponse`), any other
its own `XOutput`, whose `response` field holds the `Response`.

**Ids.** A component whose egui counterpart requires an id takes `id_salt: impl Hash` in
its constructor (modals and the toaster on `Modal`/`Area`, the sidebar on `Panel`,
select and native-select like `ComboBox`, chart on `egui_plot::Plot`). Any other
component offers `.id_salt(impl Hash)` exactly when it keeps state across passes beyond
egui's own per-widget focus and animation state, or wraps an egui widget that offers
one. Floating, panel and app-level ids are global (`Id::new(salt)`, as
`Panel::left(id)`); in-flow ids are scoped (`ui.make_persistent_id(salt)`, as
`TextEdit::id_salt`).

- A component with a state type defaults, as egui's stateful containers, to a fixed
  salt per component (`"accordion"`, as `ScrollArea`'s `"scroll_area"`) or to its label
  (as `CollapsingHeader`); any other keeps the default of the egui widget it wraps, or
  the auto id for transient state (a caret, an active cell), as `TextEdit`.
- Its `Response` carries the id, and an output type has an `id` field (as
  `ScrollAreaOutput { id, .. }`).
- Two components with one id share their state: the component calls
  `Context::check_for_id_clash`, as `ScrollArea` does, which shows egui's warning in
  debug builds, and its docs say that two in one `Ui` need `.id_salt`.

**Memory-owned state.** A state in memory with an optional binding (axiom 3:
`.open(&mut bool)`, `.value(..)`, `.index(&mut usize)`; `.default_<state>(..)` with
upstream's default) has one state type `XState` (`PopoverState`, `CarouselState`) for
code that reads or changes it at run time. State in memory only has none.

- `XState` has `CollapsingState`'s members as egui has them, named after the state:
  `load`, `load_with_default_<state>`, `store`, `remove`, `id`, the getter (`is_open()`,
  `index()`) and `set_<state>`. `load` takes the id the component reports (`None` before
  the first pass); an overlay on a caller's trigger loads by the trigger after it is
  drawn (`PopoverState::load(ctx, &trigger)`). `store` also requests a repaint, so a
  flag's `toggle()` takes no `Ui`.
- A value stored through `XState` reaches the binding on the next call; when both
  changed, the binding wins.
- A set binding is the initial value; `.default_<state>` applies only without one, while
  memory holds no value, as egui's `CollapsingHeader::open(Some(..))` wins over
  `default_open`. Setting both fails a `debug_assert!` (axiom 6).
- State persists as egui persists its own: in-flow state (disclosure, panels, layout,
  view) whenever egui's `persistence` feature is on, as `CollapsingState::store` uses
  `insert_persisted`; an overlay's state never, as egui's popups. A stored value of the
  caller's type is bound by `egui::util::id_type_map::SerializableAny`, so it needs serde
  exactly when that feature is on. Across restarts the binding is the plain path, not
  `XState`.

**Shortcuts.** A shortcut takes the builder's value form and content only, never a
variant (no `separator_vertical`). It takes an id exactly when the builder requires one.
Its name follows axiom 2, and its parameters follow egui's order: `checkbox(ui, &mut b,
text)`, `switch(ui, &mut b, text)`, `radio_value(ui, &mut v, x, text)`.

### Leaf

A widget that draws itself and holds no caller content: display leaves (badge, kbd,
separator, progress) and value leaves (checkbox, switch, toggle, slider, input, select,
native-select, tabs list, toggle-group, pagination, calendar).

- A value leaf binds the caller's value in its constructor. It writes the binding only
  in response to user input, then calls `mark_changed()`; the caller reads `changed()`.
- A leaf with more to return also has `show(ui)`, as `TextEdit::show`; `ui.add` still
  returns the `Response`.
- Shortcut when the constructor arguments are all a common call needs, and for every
  value picker over a list or a range. A widget that needs more than its constructor
  holds gets none.

```rust
ui.add_enabled(ready, Button::new("Save").variant(ButtonVariant::Outline).icon(icons.check));
if switch(ui, &mut self.notify, "Email notifications").changed() { self.save(); }
```

### Container

A component that lays out caller content in its own surface in the flow of a `Ui`: card,
alert, field, accordion item, collapsible, scroll area, sidebar.

- It takes `&mut Ui`; the method is always `show`. A mirrored type keeps egui's `show_*`
  variants (`ScrollArea::show_rows`).
- Parts that only render data are setters on the root (`.title`, `.description`, media,
  bubble reactions); their part fns (`card_title(ui, ..)`) stay for custom layouts.
- A component whose surface encloses the caller's content keeps a caller binding for
  the call, as `Window::open` does, so a content closure that reaches the same owner
  does not compile: the optional binding of a popover, an accordion or a collapsible
  when the caller sets one. Its docs show egui's local-copy idiom for that case (`let
  mut open = self.open; …; self.open = open;`).
- Where upstream's content is not inside a surface the component owns (tab panels beside
  the tab list), the component is a leaf for what it draws plus a content part fn the
  caller calls after it, so the borrow ends first.
- Groups without options are part fns (`kbd_group`, `message_group`); groups with
  options are containers (`ItemGroup`).
- A component with free content offers both `ui.add(X::new(text))` and
  `X::new(..).show(ui, |ui| ..)` where upstream demos use both.

```rust
Card::new().title("Create project").show(ui, |ui| {
    card_footer(ui, |ui| { if ui.add(Button::new("Deploy")).clicked() { deploy(); } });
});
ui.add(Tabs::new(&mut self.tab, &[(Tab::Account, "Account"), (Tab::Password, "Password")]));
tabs_content(ui, |ui| match self.tab { Tab::Account => self.account_ui(ui), Tab::Password => self.password_ui(ui) });
```

### Anchored overlay

A panel placed against a trigger: popover, tooltip, hover-card, menus, the list of a
picker. Every one joins the crate overlay stack.

- It takes the trigger by `&Response`. A call that draws its own trigger returns
  `InnerResponse<Option<R>>`.
- Placement on every anchored overlay, list pickers included: `.align(RectAlign)` and
  `.gap(f32)`. Hover overlays offer the delays upstream offers (axiom 1): `.open_delay`
  for `delayDuration` and `openDelay`, `.close_delay` for `closeDelay`.
- `.open(&mut bool)` binds the open flag, on hover overlays too, and `.default_open(bool)`
  sets its initial value. A trigger gets its `expanded` look without a second binding.
- `.id_salt` tells several overlays on one trigger apart; it does not make the overlay
  reachable without the trigger.
- A closure shortcut exists only where egui has the counterpart helper, and takes its
  shape, return type included, and its name by axiom 2: `dropdown_menu`, `menubar_menu`,
  `context_menu` (egui `menu_button`, `Response::context_menu`) and `tooltip(resp, text)`
  (egui `on_hover_text`). A helper that decorates a trigger takes it by value and returns
  it.

```rust
Popover::new(&resp).open(&mut self.popover_open).show(|ui| { ui.label("Hi"); });
let r = tooltip(ui.add(Button::new("?")), "Help");
let r = dropdown_menu(ui, "Options", |ui| { ui.add(MenuItem::new("Copy")) });
```

### Modal

A floating overlay with a backdrop: dialog, alert-dialog, sheet, drawer, command dialog.
It takes `&Context`, as egui's floating containers do: a `&mut Ui` would hide that the
panel is not laid out there. It takes no open flag (axiom 3). `XOutput<R>` mirrors
`ModalResponse` (`response`, `inner`, `should_close()`) with the crate's dismissal
(conformance 5.2) and is `#[must_use]`.

```rust
if self.confirm_open {
    let out = AlertDialog::new("confirm").title("Delete file?").show(ctx, |ui| {
        alert_dialog_footer(ui, |ui| { alert_dialog_cancel(ui, "Cancel"); alert_dialog_action(ui, "Delete").clicked() }).inner
    });
    if out.inner { self.delete_file(); }
    if out.inner || out.should_close() { self.confirm_open = false; }
}
```

### Data item

An item the widget needs while it is closed or before it paints it: trigger text and
typeahead (select, native-select), toggle-group items, the tabs list.

- Options include `.enabled(bool)` and `.icon(..)`. Every item list takes `impl
  IntoIterator` of anything that converts into the item type: item values, `(value,
  text)` tuples, by value or by reference, so arrays, slices and iterators serve the
  builder and the shortcut alike.
- The value is plain `T`, also when the binding can be empty; no data item is written
  `Some(..)`.
- A shared item type (the generic data item) serves only where all its setters work;
  otherwise the component has its own type.
- A list of plain values takes `impl IntoIterator<Item = T>` with no item
  type.

```rust
let items = [SelectItem::new(Fruit::Apple, "Apple"), SelectItem::new(Fruit::Pear, "Pear").enabled(in_season)];
select(ui, "fruit", &mut fruit, &items);
```

### Immediate item

An item called inside its parent's closure that carries the binding itself, where items
can have arbitrary neighbours: `radio_value`, a menu's checkbox and radio items. It keeps
the egui counterpart's parameters: over an empty-capable binding the item value has the
binding's type, `radio_value(ui, &mut plan, Some(Plan::Free), ..)` over `&mut
Option<Plan>`. An item that binds nothing (a plain menu item) is a leaf in its parent's
context.

### Handle

Passed to the closure where upstream lets the caller arrange the parts (axiom 4) or the
parent holds the items' state: accordion, breadcrumb, input-otp, navigation-menu,
message-scroller, table.

- The root is called as a container, with the handle in place of the `Ui`, also where
  it has no surface of its own: `Breadcrumb::new().show(ui, |bc| ..) -> InnerResponse<R>`.
- Each handle method is an upstream part and takes its name: `bc.link(..)`,
  `bc.page(..)`, `bc.ellipsis()`; a method is `item` only where the part is `Item`. A
  part that takes an item value takes the value and its text as positional parameters
  (`acc.item(Faq::Shipping, "Shipping?", |ui| ..)`); tuples convert only in item lists
  (Data item).
- Repeated uniform children come as a count plus an index closure (carousel slides,
  resizable panes).

### Part fn

A free function for an upstream part, called inside the parent's closure: a passive part
(separator, label, heading) returns `Response`; a container part (footer, header action)
returns `InnerResponse<R>`.

- Parts are called in upstream's source order, which is also Tab and reading order. A
  part upstream places before the content (a header action, `card_action`) is called
  first, a footer (`card_footer`, `dialog_footer`) last; a part out of order fails a
  `debug_assert!`. Footers keep upstream's direction, and the caller nests a layout
  inside.
- Side slots (item and attachment actions) are the closure itself, because the main
  content there is setter data.
- A group's label is a heading part (`menu_label`), except where the group is a data
  list or hides when none of its items is shown; then the group is a container that
  carries its label.
- What a container must know about a part or child before it draws (an action's size, a
  child count, a position) it takes from the previous pass (conformance 3.2).

### Service

An app-level facility with no place in a `Ui`, such as sonner's toaster: a free function
on `&Context` returns a handle, and what happened comes back as events from a per-frame
`show(ctx)`.

### Mapping upstream parts and events

- An upstream `on<Event>` prop becomes a `Response` query where egui has one
  (`changed()`, `clicked()`), else a field of the output (`InputOtpOutput { completed,
  .. }`).
- An upstream `Close` part without a look of its own becomes `ui.close()`. A part that
  is a styled button (`AlertDialog.Cancel`, `AlertDialog.Action`) is a leaf in its
  parent's context with upstream's props, default variant and close behaviour, and its
  shortcut is the part fn (`alert_dialog_cancel(ui, text)`, an outline button that
  closes).
- A `Provider` part's settings become the defaults or the root state of what it
  configures: the tooltip provider's delay is the crate tooltip's own default; the
  sidebar provider becomes the `Sidebar` root with its state in memory.

## Conventions

What neither the concept nor a template gives, but every port needs.

### Enums and flags

- Every variant and size enum of a component derives `Clone, Copy, Debug, Default,
  PartialEq, Eq`, with upstream's default as `#[default]`. Data-carrying enums derive
  what their fields allow. Shared enums (`Orientation`, `Side`) have no `Default`; their
  default is per component.
- Variant and size enums are `#[non_exhaustive]`; closed sets are not. A public helper
  enum is not `#[non_exhaustive]`, also where it grows with the crate (`OverlayKind`,
  `RovingKeys`).
- Exclusive states with three or more values are enums.
- A flag setter takes a `bool`: `.invalid(bool)`, `.expanded(bool)`. A flag that
  defaults to `true` keeps its positive name and is called with `false`. No positional
  `bool` parameters.
- A setter without an argument exists only as a shortcut for one value of an enum
  setter: `.vertical()` is `.orientation(Orientation::Vertical)`.
- The host setters (axiom 1) are these, and a new one needs the maintainer: `.id_salt`
  (Ids); `.label` on a choice control (Selection); `.wrap_mode` (Sizing); `.sense` and
  `.link` (State flags); `.enabled` where no `Ui` reaches (Disabled); `.step(0.0)`, a
  continuous slider in egui's `step_by(0.0)` spelling; `.width`, `.desired_width` and
  `.height` where they mirror egui (Sizing).

### App variants

- Every variant enum and every size enum has an app case, built by `const fn app(name:
  &'static str) -> Self`; the enum keeps `Copy`, `Eq` and `const` construction. A
  component without a variant enum gets `XVariant` with the single built-in case
  `Default`, and the `.variant(..)` setter that takes it. A component without a size
  enum has no app sizes; its app variants carry its sizes.
- The theme defines each app variant once, from a built-in one:
  `Theme::variant(APP, BuiltIn, |r, style| ..)`, and `Theme::size(APP, BuiltIn, |r,
  style| ..)` for a size. The edit is a `fn` that captures nothing; it gets the copies of
  the recipes the base draws and the `StyleName` it builds for, so a look may differ
  per style. The theme keeps the base and the edit, not `Style`, and builds the recipes
  for its current style, so an app variant holds in every style; the light and dark
  forms of a theme share its app variants and app colours.
- The recipes reach the edit in one shape for every component: `&mut XRecipes`, one
  `Recipe` field per upstream part the variant reaches, named after the part's
  `data-slot` in snake case (`ButtonRecipes { button }`, `TabsRecipes { tabs_list,
  tabs_trigger, tabs_trigger_after }`). A part upstream draws as a pseudo-element of a
  slot takes the slot's name plus the pseudo-element's (`tabs_trigger_after`, the line
  under the active tab). The struct is `#[non_exhaustive]`, so a part added later breaks
  no edit, and each component has a test that compiles one edit.
- An edit states values per state, as a class list does: `prop.set(v)` replaces the
  unconditional value and keeps the base's state rules; `prop.on(state, v)` replaces the
  base's rules for that state, as tailwind-merge does; `recipe.recolor(from, to)` swaps a
  colour role in every value and rule of the part, opacity kept.
- App colours (a light and dark pair on the theme) give app variants colours no palette
  role has. Docs and examples name app colours and app variants through constants
  (`const BRAND: Role = Role::custom("brand");`), so a misspelled name does not
  compile. A name the theme does not define fails a `debug_assert!` and draws as the
  `Default` variant.

```rust
const DANGER_GHOST: ButtonVariant = ButtonVariant::app("danger-ghost");
const DANGER_OUTLINE: ButtonVariant = ButtonVariant::app("danger-outline");
let theme = Theme::vega_light()
    .variant(DANGER_GHOST, ButtonVariant::Ghost, |r, _style| {
        r.button.text.set(Paint::Role(Role::Destructive, 1.0)); // Ghost's hover colours stay
    })
    .variant(DANGER_OUTLINE, ButtonVariant::Outline, |r, _| r.button.recolor(Role::Foreground, Role::Destructive));
ui.add(Button::new("Delete").variant(DANGER_GHOST));
```

### Modes

- `new` builds the common mode; each other mode or alternative content has a named
  constructor (`Accordion::multiple`, `Kbd::icon_only`). `from_*` names an alternative
  input form (`Progress::from_value`, `Pagination::from_count`), as egui's
  `ComboBox::from_label`.
- Icon-only content is a mode on every component: `X::icon_only(.., icon, name)`, with
  `name` as the accessible name. Where upstream spells it as size variants, the mode
  picks the icon variant of the chosen size, and the size enum keeps the text sizes.
- An empty-capable binding on a widget that also binds `&mut T` is a mode constructor:
  `Select::optional(id, &mut Option<T>, items)`.

### Parameter types

- Text takes the type that fits what the component does with it, on a builder and on a
  data item alike: `impl Into<String>` when the component reads the text as data and
  does not only draw it (filter, typeahead, comparison, an accessible name); `impl
  IntoAtoms` when the recipe lays the text out in one row that does not wrap, with icon
  slots (button, badge, kbd, toggle, toggle-group item, tab trigger), clickable or not;
  `impl Into<WidgetText>` for text that wraps (titles, labels, descriptions, an
  accordion trigger).
- A pick list's empty text is `placeholder(impl Into<WidgetText>)`.
- Icons by value (`Icon` is `Copy`); colours as `impl Into<Color32>`; typed parameters,
  not parallel arrays.
- Units are egui's: durations in `f32` seconds (`.open_delay(0.7)`), lengths in `f32`
  points. A Tailwind step is 4 points (`spacing={1}` is `.spacing(4.0)`, `max-w-sm` is
  `.desired_width(384.0)`).

### Media and icons

- Media slots are `.icon(Icon)`, `.image(impl Into<ImageSource>)` and `.media(closure)`.
  Icon slots that may show a spinner take `impl Into<Glyph>`.
- Crate widgets and data items show icons through typed `.icon` slots, painted in the
  recipe's state colour. An `IconAtom` in a crate widget's content takes the same
  colour, unless the caller gave it one (conformance 2.3). egui hosts get crate icons
  through `IconAtom(icon)`, an image atom tinted with a caller colour or the text colour.
- `IconSlots` names a slot per shape, plus a role-named slot wherever an icon library
  uses another icon for one role than for the shared shape (`calendar_prev`,
  `calendar_next`, `select_trigger`). A slot whose meaning changes gets a new name.
  `IconSlots` is `#[non_exhaustive]`.

### Disabled

- Disabled state comes from the `Ui` (`ui.add_enabled`, `add_enabled_ui`); a widget
  reads it from its `Response` in one place.
- A component also takes `.enabled(bool)` exactly when upstream gives it a `disabled`
  prop whose effect a disabled `Ui` does not reproduce: the prop leaves part of what the
  component holds interactive (an accordion item's trigger, not the caller's panel), or
  the component has no `Ui` a caller could disable (a data item, an overlay on a
  caller's trigger).
- `.enabled(false)` does what the prop does, no more; closure items take
  `add_enabled_ui`.

### Selection

- A choice binds `&mut T` with `T: PartialEq` (+ `Clone` where the widget holds a list);
  multiple selection binds `&mut Vec<T>`. Domain values stay domain types (`f32`,
  `Date`, a 1-based page). A component that owns and validates the answers itself keeps
  them in its own state type (questionnaire: indices in `&mut QuestionnaireState`).
- A choice that can be empty binds `&mut Option<T>`. A widget that can clear its value
  by itself is empty-capable only (toggle-group single, accordion single, calendar
  single `&mut Option<Date>`).
- Deselect by a second click has the setter `.allow_deselect(bool)` (select
  `allowDeselect`, calendar `preventDeselect` inverted), only where upstream has the
  prop and the binding can be empty.
- The flag that marks a caller-chosen item is `selected(bool)`, as egui's
  `Button::selected`.
- Choice controls (checkbox, switch, radio item) take an optional own label,
  `.label(impl Into<WidgetText>)` (conformance 4.5).

### Sizing, orientation, placement

- A dimension the style sets is a look (axiom 8). Where the style leaves the extent to
  the parent (`w-full`, `w-fit`, no width), the caller's `Ui` gives it: a widget that
  fills takes the `Ui`'s width, and a content-sized widget fills a justified layout
  (`ui.add_sized`), as egui's `Button`.
- A width setter exists only for an extent from where the widget sits, as a host setter
  that mirrors an egui setter, and takes egui's name, one word per widget: `.width(f32)`
  on a content-sized widget (select and native-select as `ComboBox::width`),
  `.desired_width(f32)` on one that fills (input and textarea as
  `TextEdit::desired_width`, progress as `ProgressBar::desired_width`), never both
  (conformance 3.1 says which). `f32::INFINITY` means fill. A decorative fill takes no
  width setter. A height setter exists on the same terms (chart as `Plot::height`).
- Size variants are per-component enums whose middle value is `Default`. `size` is a
  pixel size only where it mirrors egui's (`Spinner::size(f32)`).
- Label offers `.wrap_mode(egui::TextWrapMode)` for a mode other than wrapping; so does
  every part drawn through Label.
- One crate `Orientation { Horizontal, Vertical }`, set with `.orientation(..)` or the
  `.vertical()` shortcut, as egui's Slider.
- Panels on a window edge take the crate `Side`. Start and end placements use
  `egui::Align` (`Align2` for corners), set by a setter named for what it aligns. The
  crate is LTR only; placement types are egui's, whose names are physical.
- Where upstream makes a responsive mode an opt-in (field's `orientation="responsive"`),
  the crate does too (`.responsive(bool)`). Modes shadcn neither styles nor demos are
  left out.

### State flags and validation

- A `State` flag exists for each state a recipe styles, and only then (porting standard
  rules 2 and 3); its meaning is the upstream attribute it stands for (conformance 2.9).
- `invalid` exists where a recipe styles `aria-invalid`; a group or a Field passes it to
  the widgets inside. Validation is `.invalid(bool)` plus `.error(text)`.
- Display widgets become clickable with `.sense(Sense)`; `.link(bool)` gives the link
  look and role (conformance 4.1).

### Names and public surface

- Part functions and part types carry the component prefix plus upstream's part name
  (`card_title`, `menu_separator`, `TabsTrigger`, `SelectItem`). A helper type with
  another meaning than an egui type does not take its name.
- A public name that differs from upstream's carries `#[doc(alias = "<upstream name>")]`,
  so rustdoc search finds it (`hint_text` for `placeholder`, `open_delay` for
  `delayDuration`).
- A helper is `pub(crate)` unless a port into an app (port-component's in-app target,
  which uses public API only) needs it to meet these rules. Then it is public, and a
  public helper struct is `#[non_exhaustive]` with a constructor and setters, no public
  fields.
- No `#[deprecated]` aliases or forwards before 1.0: a rename or removal breaks at once,
  and CHANGES.md gives the upgrade step.

### Scrolling

Every crate component that scrolls uses the crate `ScrollArea`, and so do demos and docs
where upstream scrolls.
