# The shadcn-egui Claude Code plugin for 0.4

## Goal

The `egui-shadcn` plugin (0.3.2) copied a component module into a project.
Since 0.4.0 the components are crates on crates.io, so the plugin's
instructions no longer match the code. This spec rewrites the plugin for the
crates, renames it to `shadcn-egui`, and ties its version to the crate
version. The 0.4.0 release waits for this work, so the release notes cover
the plugin as well.

## Decisions

- The plugin holds two skills, named after their purpose:
  - `shadcn-egui:build-ui`: build or restyle an egui UI with the crate.
  - `shadcn-egui:port-component`: port a missing shadcn component, into the
    app or into this repository.
- The port skill serves both targets with one standard. In an app it uses
  only the crate's public API and builds the recipes a new component needs
  inside the app; upstream it uses the full repository tooling.
- The plugin version equals the crate version. Create release PR bumps it
  through `version_files`.
- The marketplace entry installs the plugin from the release tag
  (`"ref": "vX.Y.Z"`), so users get the skills that match the crate on
  crates.io, never unreleased text from `main`.
- Installation is through the repository's own marketplace. An entry in the
  oposs marketplace is out of scope.

`skills/egui-shadcn/` is removed; `git mv` keeps the history of the files
that move.

Every code fence in the skills carries a language tag (`rust`, `bash`,
`toml`, `text`), because rustdoc compiles an untagged fence as Rust (see
Checks).

## Skill `build-ui`

Description (the trigger): building or restyling a Rust egui GUI from a
shadcn or web design (screenshot, component code, preset code or
description) with the `shadcn-egui` crate; also an egui app that renders
without a GPU and is slow, pins a CPU core, redraws late or misroutes pointer
input.

The SKILL.md workflow:

1. Add the crate with `cargo add shadcn-egui@<version>`, where `<version>`
   is the `version` in `${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json`,
   and only the `font-*` and `icons-*` features the design uses. The crate
   does not re-export egui: the app depends on the egui version the crate
   uses (`egui = "0.34"` for 0.4). The crate needs no `eframe`; it works with
   any egui integration.
2. Set the look once, right after the egui context exists:
   - a preset code from ui.shadcn.com:
     `Preset::from_code(..)?.apply(ctx, Mode::Dark)`, with the features the
     preset names;
   - a `components.json`: `Preset::default()` with `.style(..)`,
     `.base_color(..)` and `.icons(..)` from its `style`,
     `tailwind.baseColor` and `iconLibrary`, `.radius(..)` from `--radius`
     in the project's CSS when given, then `.apply(ctx, mode)`;
   - nothing given: `Theme::vega_dark().apply(ctx)`.

   A preset that names a font or icon set whose feature is off falls back to
   Inter or Lucide and says so through the `log` crate; the app installs a
   logger (for example `env_logger`) to see it. An app with fonts of its own
   uses `Theme::apply_with_fonts`. Apply again only when the mode or preset
   changes; read tokens with `Theme::current(ctx)`.
3. Decompose the design top-down: app shell, panels, the layout intent of
   each region, components and variants, token deviations.
4. Map with the references, `layout-map.md` first.
5. Build from `shadcn_egui::components` and `shadcn_egui::layout`. A missing
   component goes through `shadcn-egui:port-component`, not through ad hoc
   painting.
6. Verify visually: render a PNG and compare it with the design. The
   reference loop is an `egui_kittest` snapshot test as a dev-dependency;
   the skill carries a short test template. An app with its own screenshot
   path may use that instead.
7. Acceptance: the restraint of `reference::settings_ui` and the gallery
   example; the literal scan with its positive control (kept from 0.3);
   project deviations go into the theme construction
   (`let mut s = Style::nova(); s.button.… = …`), never into copies of crate
   code.

Kept from 0.3: the hard rules (single-pass layout, no `available_width()`
arithmetic, no invented state colours, `widget_info` on custom-painted
widgets) and the CPU-rendering reference. Removed: vendoring, the
`registry/` steps, the instruction to depend on egui_extras.

`references/presets.md` covers `Preset::from_code`, `to_code`, the builder
methods, `apply`, `apply_with_fonts`, the font and icon features and the
fallbacks (feature off, translucent menu colour, `sera` falls back to
`nova`, shadcn-svelte.com codes are not supported).

`references/icons.md` covers `IconLibrary`, the `icons-*` features,
`IconView` and the icon slots of components.

## Skill `port-component`

Description: a shadcn component or layout helper the UI needs is missing
from `shadcn-egui`; port it to the crate's standard, into the app or into
the shadcn-egui repository.

The shared part in SKILL.md:

1. Choose the target and say why. Upstream when working in a shadcn-egui
   checkout or when the user wants the component in the crate; in the app
   otherwise.
2. Source: the base `.svelte` file of shadcn-svelte at the commit in
   `tools/stylegen/PIN` and the bits-ui primitive (the skill gives the URL
   forms). Never port from memory or a screenshot.
3. Inventory: the `cn-*` markers and the styled states.
4. Mapping: markers to recipes (a `Style` field upstream, an app-local
   `Recipe` in the app), states to `State` flags, `pick` in the order
   upstream joins the classes, `components::shared::interaction_state` for
   hover, active and focus.
5. Base classes quoted verbatim as `// base: "…"`; no style value in code
   without a quote or a `// token-ok:` comment.
6. egui sizing: the widget sizes itself before placement; size does not
   change on hover.
7. The behaviour list from the bits-ui primitive (with the Slider example)
   and the interaction-state rules, both kept from 0.3.
8. Snapshots in dark and light for each style in use; every PNG opened and
   compared with the shadcn-svelte docs page.
9. Dependency discipline: no new runtime dependency without a stated reason
   and the user's consent.

`references/in-app.md`:

- The public API: `Theme::current`, the `Style` fields of existing markers,
  `style::recipe::{pick, Recipe, Prop, State}`,
  `components::shared::interaction_state`.
- New markers: `Style` holds only the markers of ported components, so a new
  component's markers (`cn-radio-group`, …) have no field. The app builds
  one `Recipe` per marker for each style it uses, with the values read from
  that style's `style-<name>.css` in shadcn-svelte at the pinned commit, and
  a `// style: "<css class string>"` quote above each recipe. The component
  selects the recipe for `Theme::current(ctx)`'s style; a style without a
  recipe falls back to the first one and logs a warning.
- Where the file goes, for example `src/ui/components/<name>.rs`, with its
  recipes in the same file.
- The token check is the literal scan from `build-ui`.
- `// base:` and `// style:` quotes stay in the code, so an upstream port
  later can check them.
- At the end the skill offers to open a PR to `oetiker/shadcn-egui`, which
  needs the user's approval; upstream, the app-local recipes become
  generated `Style` fields.

`references/upstream.md`:

- `tools/stylegen/markers.txt` and `stylegen generate`; `stylegen generate`
  and `stylegen drift` need a shadcn-svelte checkout at `tools/stylegen/PIN`
  and a shadcn-ui checkout at `tools/stylegen/PIN_REACT`.
- The token scan in `crates/shadcn-egui/tests/tokens.rs` covers every file
  in `src/components/` and `layout.rs`, so a new file is checked without
  registration.
- `common::snapshot_all`; `stylegen drift` prints `drift: clean`; no
  unsupported class in `tools/stylegen/reports/<style>.md`.
- A row in `skills/build-ui/references/component-map.md`, a CHANGES entry,
  the gates from `CLAUDE.md`.
- The icongen command that regenerates the icon crates and
  `crates/shadcn-egui/tests/icons/lucide.rs`, moved from the old
  `icons.md`.

## Checks

- Every `rust` code block in `skills/*/SKILL.md` and
  `skills/*/references/*.md` compiles as a doctest, through
  `#[cfg(doctest)] #[doc = include_str!(…)]` items in
  `crates/shadcn-egui/src/lib.rs`. The skill files are outside the crate
  package (`include = ["src/**", …]`); `cfg(doctest)` removes the items
  before `include_str!` expands, so `cargo build`, `cargo package` and
  `cargo publish` never read them. `cargo test --doc` on an unpacked
  `.crate` fails to find them; that is accepted.
- Snippets are small complete functions without hidden `# ` lines, which
  GitHub would show. They compile with default features and with
  `--all-features`, so a snippet does not depend on a `font-*` or `icons-*`
  feature. A block that cannot compile on its own (a signature sketch) is
  marked `rust,ignore` and stays rare.
- `crates/shadcn-egui/tests/skills.rs` (plain string matching, no new
  dev-dependency):
  - every module in `src/components/` except `shared` and `icon_raster` has
    a row in `component-map.md`;
  - every `font-*` and `icons-*` feature the skills name exists in
    `crates/shadcn-egui/Cargo.toml`;
  - the version in `plugin.json`, the `version` and `ref` of the plugin
    entry in `marketplace.json` and the workspace version agree.
- `.github/repo-infra.json` gets three `version_files` entries; each regex
  depends on the file's indentation:
  - `plugin.json`: pattern `^  "version": "[^"]*"`, replacement
    `  "version": "$VERSION"`;
  - `marketplace.json`: pattern `^      "version": "[^"]*"`, replacement
    `      "version": "$VERSION"`;
  - `marketplace.json`: pattern `^        "ref": "v[^"]*"`, replacement
    `        "ref": "v$VERSION"`;

  each with a `verify` pattern of the replaced line.
- The `ri-ci-claude-plugin` CI job checks `plugin.json`; `tests/skills.rs`
  is the check on `marketplace.json`.
- Trial run before the merge: a headless
  `claude -p --plugin-dir <branch checkout>` session in a scratch app with a
  path dependency on the branch's `crates/shadcn-egui` builds a small screen
  from a preset code with `build-ui` and ports RadioGroup into that app with
  `port-component`. The controller reviews the PNGs and fixes what the
  skills left unclear. Nothing from the trial run is committed.

- `CLAUDE.md`: the introduction no longer calls the plugin frozen at 0.3.2;
  drop "`.claude-plugin/*.json` stay at 0.3.2"; add that the skills name
  crate APIs, so an API change updates the skills in the same PR; the

  the marketplace `ref` follow the crate version through Create release PR.

  `/plugin install shadcn-egui@shadcn-egui`.

  and builds on the crate instead of copying code. An existing install is

  replaced.

  place of the icongen command.

## Release order

`release-publish.yml` runs on every push to `main` that changes
`CHANGES.md` and fails while CHANGES and the crate versions disagree;
Create release PR refuses a commit with a failed check. Hence:

1. This spec, a plan, the implementation on `feat/plugin-0.4`; one PR with
   the CHANGES entry; merge commit. Its "Tag and publish" run fails, as on
   `af5dcd7`.
2. Then PR #2 (no-changelog) merges; its merge commit has no failed check.
3. Trusted Publishing registration (the user's script).
4. Create release PR on the merge commit of PR #2 with bump `feature`
   (0.3.2 to 0.4.0), the release PR, Tag and publish. The `v0.4.0` tag that
   the marketplace entry names exists from then on.

## Out of scope

The oposs marketplace entry, the gallery as WebAssembly, and the deferred
bugs listed in the 0.4 handoff.
